# 新建项目为什么要联网？从一次报错到两种创建方式

一次很普通的创建项目命令失败了。顺着报错往下查，牵出了基线最核心的一条设计：**项目不是生成完就和基线没关系了**。这篇文章记录排查过程、背后的道理，以及我们最后做的改动：`new-project` 现在同时支持“一次性拷贝”和“可持续升级”两种方式。

## 起因：一条报错

在基线仓库根目录执行：

```bash
sh bin/new-project.sh /Users/wanghuan/Documents/ai_workspace/ane-admin-test
```

输出：

```text
! 当前提交没有标签，已固定为提交 042c72e2bf3c2ceedb9b4a719b3a2ee12d8e2063。该提交必须已经在基线远端上。
✗ 基线来源 git@github.com:wanghuanlab/ai-native-engineering.wanghuanlab.com.git 上找不到引用 042c72e2bf3c2ceedb9b4a719b3a2ee12d8e2063。请确认标签或分支已推送。
```

第一行是警告，第二行才是退出原因。

## 排查：脚本拦住了一个只在本机的提交

`new-project` 在复制任何文件之前，先做两步：

1. **确定版本。** 没有传版本参数，也没有设置 `--ref` 或 `BASELINE_REF` 时，脚本先找当前提交上的标签。找不到，就改用当前提交的完整哈希，并打印第一行警告。
2. **核对远端。** 用 `git ls-remote` 列出基线远端（默认是仓库的 `origin`）的所有分支和标签，看有没有一个指向这个哈希。没有，就报第二行的错并退出。

当时仓库的状态正好对上：

| 位置 | 状态 |
| :--- | :--- |
| 本机 `main` | 停在 `042c72e`，比 `origin/main` 超前 6 个提交 |
| GitHub `main` | 停在 `05f0825` |
| 标签 | 一个都没有 |

`git ls-remote` 能正常返回，说明网络和 SSH 权限都没问题。问题只有一个：脚本要固定的那个提交还没推上去，GitHub 上没有任何引用指向它。

## 疑问：新建项目，为什么和 Git 版本有关？

这是排查中最自然的疑问：新建项目不就是复制一份模板吗？离线为什么不能用？

答案在于，基线有两种可能的“新建项目”方式，它们的目标完全不同。

**方式 A：一次性拷贝。** 就像从 U 盘复制一个文件夹，复制完两边就没关系了。不需要来源地址和版本，离线也能用。代价在以后：基线修了一个 bug、改了门禁规则或加了插件，已经建好的十几个项目只能靠人一个个对比、手工合入。

**方式 B：可持续升级的模板。** 基线是团队的工程基线，规则、门禁、脚本、插件机制会不断迭代。它要的效果是：基线发布新版本后，每个项目执行一条 `scripts/sync-baseline.sh <新版本>`，就能把新改动合并进来，同时保留项目自己的业务修改。

基线原来只支持方式 B。

### 升级时到底发生了什么

假设项目从基线 `v0.1.0` 生成，后来基线发布了 `v0.2.0`。项目里同一个文件，可能两边都改过：

```text
                基线 v0.1.0 的原始文件（共同起点）
                 /                        \
   基线作者改成 v0.2.0                项目组自己也改过
 （比如门禁加了一条检查）          （比如加了业务配置）
                 \                        /
                    合并后的结果：两边改动都保留
```

Copier 升级时做的就是这种三方合并：

1. 取出**旧版模板** `v0.1.0`，也就是项目当初生成时的样子。
2. 取出**新版模板** `v0.2.0`。
3. 计算模板从旧版到新版改了什么。
4. 把这些改动套到项目当前的文件上，项目自己的修改保持不变。

关键在第 1 步：它必须能一字不差地重新拿到当初生成项目用的那份模板。拿不到，就分不清项目里哪些内容是模板原有的、哪些是项目组后来改的，结果要么覆盖掉项目的修改，要么根本没法合并。

所以创建项目时，Copier 会在项目里登记一份“出生信息” `.baseline/copier-answers.yml`：

```yaml
_src_path: "git@github.com:wanghuanlab/ai-native-engineering.wanghuanlab.com.git"   # 从哪来
_commit: 2b387da                                                                    # 哪个版本
project_code: park                                                                  # 创建时回答的问题
```

来源地址回答“旧版模板去哪里取”，版本回答“取哪一版”，缺一不可。

### 为什么必须是远端地址，而且必须已经推送

升级不一定在创建者的电脑上做，项目通常交给项目组，由同事在自己的电脑上执行 `sync-baseline`。那台电脑需要：

- **地址能访问。** 如果记录的是 `/Users/wanghuan/Documents/...`，同事的电脑上没有这个目录。基线早期就踩过这个坑，见 [基线维护指南](../../handbook/05-基线维护指南.md)。
- **版本能取到。** 如果记录的是 `042c72e`，但它只在创建者本机，同事从 GitHub 拉下来的仓库里根本没有它。

脚本在创建时就拦下，是为了不生成一个几个月后才发现“没法升级”的项目。这个限制不是因为“新建”这个动作需要联网，而是要保证项目以后还能升级。

## 改动：两种方式都支持

道理讲通了，但需求也是真实的：离线试用、做演示，或者确定不跟随基线升级的项目，确实只需要方式 A。于是 `new-project` 增加了 `--mode` 参数：

| 方式 | 命令 | 网络 | 以后能否 `sync-baseline` |
| :--- | :--- | :--- | :--- |
| B：可持续升级（默认） | `bin/new-project.sh <目录>` 或加 `--mode sync` | 需要访问基线远端 | 能 |
| A：一次性拷贝 | `bin/new-project.sh <目录> --mode copy` | 不需要 | 不能 |

不加参数时行为和以前完全一样。

### 操作方式

正式交给项目组的项目，用方式 B。最好先给基线打标签并推送，再按标签创建：

```bash
git tag -a v0.2.0 -m v0.2.0 && git push --follow-tags
bin/new-project.sh ~/work/park v0.2.0
```

离线试用或演示，用方式 A：

```bash
bin/new-project.sh ~/work/park-demo --mode copy
```

两种方式都支持非交互参数和创建时勾选插件，例如：

```bash
bin/new-project.sh ~/work/park-demo --mode copy --defaults \
  -d project_code=park -d project_name=智慧园区 -d tech_lead=wanghuan \
  -d 'plugins=["admin"]'
```

Windows 用 `bin\new-project.cmd`，参数相同。

### 两种方式的执行逻辑

**方式 B（`--mode sync`）**

1. 来源：`--source` 或 `BASELINE_SOURCE`，否则取基线仓库的 `origin`，并去掉 URL 里的用户名和令牌。本机路径直接拒绝。
2. 版本：位置参数、`--ref` 或 `BASELINE_REF`；否则用当前提交上的标签；再否则用当前提交的完整哈希。
3. 用 `git ls-remote` 核对远端能否访问、版本是否存在。不通过就退出，并在报错末尾提示：只想离线生成的话，可以改用 `--mode copy`。
4. 执行 `copier copy --vcs-ref <版本> <来源> <目录>`，项目里登记远端地址和版本。

**方式 A（`--mode copy`）**

1. 来源默认是本机的基线目录，不做任何远端检查。
2. 没传 `--ref` 时用 `HEAD`。原因是 Copier 在不指定版本时会取最新的标签，那可能是很久以前的版本；而 `HEAD` 代表“当前这份文件”，连未提交的改动也会带进项目。
3. 执行 `copier copy`，照常运行初始化任务（建 Git 仓库、装钩子、生成 AI 配置、装入勾选的插件）。
4. 在 `.baseline/copier-answers.yml` 顶部写入一行标记：

```yaml
# 由基线一次性拷贝生成（方式 A），不跟随基线升级。以下仅记录创建时的来源和答案。
_baseline_mode: copy
```

项目代号、包名、方言等答案照样保留，插件脚本和开发脚本仍要读取它们。

### 一次性拷贝的项目执行同步会怎样

`sync-baseline` 一开始就检查这个标记，看到后直接退出，不改任何文件：

```text
✗ 本项目以一次性拷贝方式（方式 A）创建，没有固定的基线来源和版本，无法做三方合并。
  需要跟随基线升级的项目，请用 bin/new-project.sh <目录>（方式 B，默认）重新创建，再迁入业务代码。
```

与其让 Copier 在一个来源是本机路径、版本可能带未提交改动的记录上勉强合并，不如明确告诉使用者：这条路走不通，该换哪条路。

## 验证

- 方式 A：在不访问远端的情况下生成项目，首次提交通过提交钩子；勾选示例插件能正常装入；`sync-baseline` 按预期拒绝并说明原因。
- 方式 B：参数非法、引用未推送时都会给出明确报错和下一步提示。把积压的提交推送到 GitHub 之后，再用默认方式创建，项目登记的来源是 GitHub 地址，版本是 `2b387da`，最初那条报错消失。
- `bin/selftest.sh source` 新增方式 A 的用例：创建、检查标记、确认同步被拒绝。整套 `source` 自测通过。

## 怎么选

- **交给项目组长期维护的项目：方式 B。** 先打标签、推送，再按标签创建。以后基线的门禁、规则和插件更新，都能用一条 `sync-baseline` 合入。
- **离线环境、临时试用、演示、一次性交付：方式 A。** 创建最快、不依赖网络，但要接受以后基线的改动只能人工合入。
- **用方式 A 建了项目，后来又想升级：** 用方式 B 重新创建一个项目，再把业务代码迁进去。这比事后补登记“出生信息”更可靠。
