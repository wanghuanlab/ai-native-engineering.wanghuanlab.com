# 需求入库与澄清

## 适用条件

- 工程师转述了产品经理的口头需求，或提供了需求文档、原型截图。
- 已有能力需要变更（需求变更也从这里开始）。

## 必读文件

1. `docs/context/glossary.md`（术语）
2. `docs/specs/` 下与需求相关的能力规格
3. `docs/changes/` 下进行中的变更包（避免重复或冲突）

## 步骤

1. 取一个英文短名（小写加连字符，如 `visitor-approval`），运行 `./scripts/new-change.sh <短名> --intake-only`，生成 `docs/requirements/REQ-<日期>-<短名>/`。
2. 把原始材料放进 `raw/`。口头需求写成 `raw/verbal.md`，记录谁、什么时间、通过什么方式、原话是什么。
3. 按 `docs/_templates/intake.md` 填写 `intake.md`（示范见 `docs/_templates/examples/REQ-20261015-visitor-approval/intake.md`）：背景、目标、涉及的角色、涉及的能力、范围内与范围外。
4. 对照现有规格逐条检查，列出澄清问题，每个问题写清楚：
   - 问题本身
   - 为什么要问（不确定会影响什么）
   - 建议的默认答案
   重点检查：状态流转是否闭环、权限边界、存量数据如何处理、与现有规则是否冲突、异常情况怎么办。
5. 判定任务级别 S / M / L，写进 `intake.md` 并说明理由。
6. 把澄清问题交给工程师，由工程师向产品经理求证。答复回来后，把答案逐条记录在问题下方。

## 输出

- `docs/requirements/REQ-<日期>-<短名>/raw/`
- `docs/requirements/REQ-<日期>-<短名>/intake.md`

## 完成标准

- 每个澄清问题都有答案，或明确标记为"本期不做"。
- 任务级别已判定。
- 下一步：S 级直接实现；M、L 级执行 Skill `spec-change`。

## 必须停下来

- 需求与现有规格冲突，而原始材料中没有说明以哪个为准。
- 无法判断需求属于哪个能力或模块。
