# 插件机制

可选功能（RBAC、手机应用、微信小程序、地图组件等）以插件进入项目。本文是基线维护组的决策记录：插件是什么、清单怎么写、基线留了哪些扩展点。提案见 `proposals/20261109-plugin-mechanism.md`。

## 已确认的决定

1. **源码注入。** 插件代码复制进项目，包名变成 `<包名前缀>.<项目代号>.<模块>`，之后归项目所有。不采用运行时插件（PF4J、OSGi、微前端），也不把插件发成固定包名的 Maven / npm 制品。
2. **每个插件是一份独立的 Copier 模板。** Copier 的 Git 地址不能指向仓库子目录，所以发布时插件单独成库、打标签。开发期和 `bin/selftest.sh` 用本机目录。升级走 `copier update` 的三方合并，因此插件模板要保留答案文件。
3. **两种装入方式同一条路径。** 创建项目时在 `plugins` 多选题里勾选，或项目建好后执行 `scripts/plugin.sh add <名称>`（Windows：`scripts\plugin.cmd`、`scripts\plugin.ps1`）。升级：`scripts/plugin.sh update <名称> <版本标签>`。
4. **第一个业务插件只做 RBAC 核心**（用户、角色、菜单/按钮、部门、岗位、数据权限、JWT 登录）。字典、参数、操作日志、定时任务、代码生成、监控不做。RuoYi-Vue / RuoYi-Vue3 只作业务参考，不提交进本仓库。
5. **权限是横切能力，注解放在 `common`。** 业务模块不依赖具体插件。没装认证插件时，`@RequiresPermission` 全部放行，示例模块和集成测试保持原样。

不采用的做法：用 `{% if %}` 把每个功能都写进基线模板。那样每加一个功能基线就膨胀一次，而且项目建好之后不能再加。

## 目录约定

插件仓库（开发期可以先放在本仓库 `plugins/<名称>/`，发布时拆出去）：

```
plugins/<名称>/
  copier.yml          # 渲染变量；答案写到项目的 .baseline/plugins/<名称>.yml
  plugin.yml          # 清单：版本、基线范围、依赖、要插入的片段
  template/           # 与项目同构的目录，.jinja 会渲染
```

本仓库用 `template/.baseline/plugin-catalog.yml` 登记可安装的插件。这个文件会复制进每个项目，随基线更新。字段：

| 字段 | 含义 |
| :--- | :--- |
| `description` | 一句话说明 |
| `local` | 相对基线检出根目录的路径。只有项目记录的基线来源是本机目录时才用，供维护者自测 |
| `git` | 发布后的独立仓库地址。来源是 Git 地址时，`plugin.sh add` 用它 |

`example` 是机制自测插件，不是业务功能。业务项目不要勾选。

## 清单 `plugin.yml`

```yaml
name: example
version: 0.1.0
summary: 一句话说明
baseline:
  min: "0.1.0"          # 项目记录的基线标签低于此版本时拒绝安装；记录的是提交哈希时不比较
requires: []            # 必须先安装的插件名
inserts:
  - file: backend/pom.xml
    marker: "<!-- @modules-end -->"
    id: module          # 幂等标记 plugin:<名称>:<id>，文件里已有则不再插入
    content: "        <!-- plugin:example:module -->\n        <module>modules/sample</module>\n"
```

`content` 里可以用 `{{ project_code }}`、`{{ project_name }}`、`{{ package_name }}`、`{{ package_path }}`、`{{ package_root }}`、`{{ dialects }}`。这是简单替换，不是完整的 Jinja。`${project.version}` 这类 Maven 占位符保持原样。

`plugin.sh add` 在插入前检查：清单 `name` 与命令一致、`requires` 已安装、基线标签满足 `baseline.min`。重复执行只核对插入点，不重复插入，也不重新复制文件。

## 扩展点

基线只提供下面这些接入位置。插件改共享文件时必须走清单插入，不能让 Copier 覆盖整个文件。

| 位置 | 标记或约定 | 谁来写 |
| :--- | :--- | :--- |
| `backend/pom.xml` | `<!-- @modules-end -->` | 新的 Maven 模块 |
| `backend/app/pom.xml` | `<!-- @module-deps-end -->` | app 对新模块的依赖 |
| `docs/context/architecture.md` | `<!-- @module-table-end -->` | 模块清单的一行 |
| `backend/app/src/main/resources/application.yml` | `# @plugin-config-end` | 插件配置，插在标记所在行之前 |
| `deploy/local/compose.yaml` | `# @plugin-services-end` | 额外的 compose 服务，作为 `services` 的同级项 |
| `frontend/apps/admin/src/plugins/<名称>/index.ts` | `import.meta.glob` | 插件前端。导出 `routes` 和 `install({ app, router })` |
| `frontend/apps/admin/src/plugins/host.ts` | `setMenuLoader` | 替换侧栏菜单。默认用静态路由的 `meta.title` |
| `common` 的 `RequiresPermission`、`PermissionChecker` | 权限 SPI | 业务代码只依赖注解；认证插件提供另一个 `PermissionChecker` |
| `common` 的 `IntegrationTestAuthentication` | 测试登录 | 没有这个 bean 时，集成测试不附加任何请求头 |
| `db/migration/<方言>/` | 见下文 | 每个启用的方言各一份同名脚本 |
| `.baseline/plugins/<名称>.yml` | Copier 答案 | 项目自有。`.baseline/**` 其余文件仍由基线托管 |

前端约定：

- 路由文件用 `import.meta.glob('../plugins/*/index.ts')` 收集 `routes`，挂到名为 `layout` 的根路由下。
- `main.ts` 用 `import.meta.glob('./plugins/*/index.ts')` 调用每个插件的 `install`。
- 没装任何插件时 glob 结果为空，菜单仍来自骨架路由，页面行为与引入该机制之前一致。
- 装了会下发菜单的插件后，插件在 `install` 里调用 `setMenuLoader`，侧栏改用该来源。

权限约定：

- 注解打在 Spring MVC 的处理方法或控制器类上，由 `PermissionInterceptor` 在进入方法前检查。
- 默认实现由自动配置注册：容器里没有别的 `PermissionChecker` 时，全部放行。
- 认证插件把自己的 `PermissionChecker` 注册成 bean 即可替换默认实现，不要改 `common` 的代码。
- `CurrentUser` 仍由认证过滤器设置。业务模块不引用插件里的类。

迁移脚本：

- 模板文件名写成 `V{{ migration_version }}__<模块>_<描述>.sql`。`plugin.sh` 把 `migration_version` 设为安装时刻（`年月日时分`，12 位），并多传一个 `migration_version_2`（下一分钟，避开已有版本）。不要在模板里写死版本号，否则项目上线后再装插件，版本会早于已执行的脚本。
- 同一插件的第二份脚本用 `migration_version_2`。安装时刻已经写进答案文件，升级时沿用，避免 Copier 认为文件被改名。
- 项目启用几种方言，模板就只渲染那几种。文件名在各方言目录中必须相同。

答案文件：

- 插件模板的 `_answers_file` 必须是 `.baseline/plugins/<名称>.yml`，不能写进项目原来的 `.baseline/copier-answers.yml`。
- 提交钩子允许提交这个答案文件。`.baseline/` 下的其他文件仍然不能在项目里改。
- 插件带来的 AI 规则写到 `.ai/project/plugins/<名称>.md`（项目自有，会被 `build-ai-config.py` 编译）。不要写 `.ai/rules/`，那是基线托管目录，项目提交会被拦截。

## 命令

```bash
scripts/plugin.sh list
scripts/plugin.sh add example                  # 按目录解析来源
scripts/plugin.sh add example --source <目录或 Git 地址> [--ref <标签>]
scripts/plugin.sh update example v0.2.0
```

升级走 Copier 的三方合并，工作区必须是干净的（改动已提交或已贮藏）。`update` 的答案文件参数必须是相对路径。

创建项目时，Copier 在 `bootstrap.py` 之后执行 `plugin.py add-selected`，对 `plugins` 答案里的每一项调用 `add`。

`add` 读取项目的 `.baseline/project.json` 和 `.baseline/copier-answers.yml`，把 `project_code`、`package_name`、`package_path`、`dialects` 等传给插件模板。

## 插件作者还要遵守的门禁

注入进项目的代码就是项目代码，要能通过 Spotless、Checkstyle、SpotBugs、ArchUnit、Modulith 和覆盖率下限。不放宽 `backend/quality/`。技术栈与主项目一致：JPA、Flyway、契约先行、MapStruct、ProblemDetail、雪花 ID、软删除审计字段。不引入 MyBatis、PageHelper、Druid、fastjson。`admin` 插件按上面的决定额外使用 Redis、BCrypt 和 JWT。

模块型插件提供后端模块、契约、迁移脚本和 `src/plugins/<名称>/`。应用型插件在 `frontend/apps/<名称>/` 增加应用；需要登录时在 `requires` 里声明所依赖的认证插件。

## admin 插件已确认的取舍

提出人于 2026-11-09 确认：

- **引入 Redis。** 验证码、刷新令牌和访问令牌注销名单放 Redis，并设置过期时间。访问令牌本身仍是无状态 JWT。
- **登录必须带验证码。** 答案只放 Redis，校验后立即删除。
- **数据权限用 JPA `Specification`。** 不使用 Hibernate Filter，也不拼接 SQL。

因此 admin 插件额外依赖这三样，基线骨架本身不依赖它们：

| 依赖 | 理由 |
| :--- | :--- |
| `spring-boot-starter-data-redis` | 验证码、刷新令牌和注销名单需要可过期的集中存储。版本跟随 Spring Boot。 |
| `spring-boot-starter-jackson` | 认证过滤器在进入控制器之前写出 `problem+json`，使用 Spring Boot 4 的 Jackson 3。显式声明，不靠 WebMVC 的传递依赖。 |
| `spring-security-crypto` | 只使用 BCrypt 做密码哈希，不引入 Spring Security 过滤链。权限仍走基线已有的 `PermissionInterceptor`。 |
| `jjwt` 0.12.6 | 签发和校验 HMAC JWT。基线没有现成的 JWT 实现。 |

不引入 MyBatis、PageHelper、Druid、fastjson，也不引入完整的 Spring Security。
