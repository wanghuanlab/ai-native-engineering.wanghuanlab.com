# ai-native-engineering：元宇宙研发中心 AI 协作工程化管理基线（方案 v2）

> 版本：v2.0 草案　｜　日期：2026-10-15　｜　适用：元宇宙研发中心全部新建项目
> 本文定义的是"团队与 AI 怎么协作"，不是某个业务系统怎么实现。

---

## 0. 需求理解与约束

### 0.1 要解决的问题

研发中心 30+ 名工程师同时交付勤务、ERP、OA、文档管理、园区管理、数字孪生可视化等多个项目，AI Coding 正在成为主要工作方式。缺少统一基线时会出现：

- 需求以口头或文档形式到达，AI 每次重新理解，变更后推翻已有设计。
- 每个项目、每个人、每个 AI 工具产出的结构、风格、数据库写法都不一样。
- 交接物（需求 → 方案 → 代码 → 测试 → 部署包）没有固定格式，出了问题无法追溯。

`ai-native-engineering` 要统一的是：**每个环节的输入、输出、格式、确认人与完成标准，以及跨项目一致的工程约定**，并把它们落成 AI 能执行、机器能检查的形式。

### 0.2 已确认的约束

| 维度 | 约束 |
| :--- | :--- |
| 技术栈 | 后端 Java + Spring Boot + JPA；前端 Vue 3 + TypeScript；数据库 PostgreSQL，信创项目为达梦、人大金仓等；Web 大屏使用 Three.js / Cesium（UE、Unity 不在范围内） |
| 需求来源 | 产品经理以口头或文档形式提供，不做系统对接 |
| 角色 | 产品经理、工程师、运维/实施；无专职测试，测试与业务验收由工程师 + AI 完成，产品经理不参与开发阶段验收 |
| AI 工具 | Cursor、Claude Code、Codex 混用；涉密项目使用国产或私有化部署模型 |
| 代码托管 | 自建裸 Git 服务器，没有合并请求（PR/MR）、CI 和受保护分支 |
| 交付环境 | 私有化部署到客户现场，多个客户版本并存；部分项目有信创要求 |

### 0.3 由约束推出的设计原则

1. **需求入库是第一道工序**：口头和文档需求必须先由工程师 + AI 整理成仓库内的结构化规格，后续一切以它为准。
2. **验收标准前置确认**：产品经理不参与开发阶段验收，所以必须在规格阶段确认验收标准；之后工程师 + AI 严格按这份标准测试和验收。
3. **为能力最弱的模型设计**：涉密项目只能用私有模型。规则写成短句、清单和示例，能用脚本生成的不交给 AI 自由发挥，偏差靠机器门禁兜底。
4. **不依赖平台能力**：裸 Git 也能跑通全部流程；以后引入 Gitea、Jenkins 等平台只是把同样的检查搬到服务端。
5. **多数据库是常态**：数据库规范按"可移植子集 + 方言目录"设计，不把 PostgreSQL 专有特性写进公共约定。
6. **按规模分级**：小改动不走重流程，否则规范会被绕过。

## 1. 定位与边界

### 1.1 基线包含什么

| 组成 | 内容 | 面向 |
| :--- | :--- | :--- |
| 研发规范手册 | 角色职责、研发流程、产物规范、工程约定、AI 协作、门禁、Git 协作、交付部署、基线治理 | 人 |
| 产物模板 | 需求记录、规格、变更提案、技术设计、任务清单、验收报告、发布说明、部署手册 | 人 + AI |
| AI 规则源与 Skills | 一份规则源，编译生成 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules/`；按研发环节划分的 Skills | AI |
| 门禁与工具 | 格式化与 Lint 配置、Git 钩子、`verify` 校验脚本、规则编译脚本、代码生成脚本、服务端钩子 | 机器 |
| 最小空骨架 | 可运行的前后端空工程、本地开发环境、部署打包脚本，不含业务功能 | 新项目 |

### 1.2 基线不包含什么

- 不包含业务功能（用户权限、组织机构等由项目自行实现，或后续单独立项为公共模块）。
- 不包含公共技术底座 SDK（错误响应、异常处理等以骨架内的源码形式提供，归项目所有）。
- 不包含 UE / Unity 等非 Web 可视化工程的规范。
- 不对接需求管理系统，不建设平台类工具（Web 管理台、多 Agent 调度平台、外部知识库问答系统）。

### 1.3 基线、骨架、项目三者的关系

```
ai-native-engineering（基线仓库，基线维护组维护，按版本发布）
 ├── 规范手册 / 模板 / 规则源 / Skills / 门禁工具 ──► 通过"同步"持续更新到项目（基线托管文件）
 └── 空骨架 ─────────────────────────────────────► 只在创建项目时复制一次，之后归项目所有
                                                        │
                                                        ▼
                                         业务项目仓库（项目组维护）
                                         ├── 基线托管文件：只能通过同步更新，项目内禁止修改
                                         └── 项目自有文件：规格、代码、项目规则，项目自主演进
```

## 2. 角色与职责

| 角色 | 职责 | 不做什么 |
| :--- | :--- | :--- |
| 产品经理（PM） | 提供需求材料；回答澄清问题；**确认规格中的业务规则与验收标准** | 不写仓库文档，不参与开发阶段验收 |
| 项目技术负责人（TL） | 判定任务分级；审批技术设计；合并前复核；合并主干；打版本、出交付包 | 不替代工程师做验收 |
| 工程师 | 对自己负责的需求从入库到验收全程负责；驱动 AI 完成规格、设计、实现、测试；对 AI 产出负最终责任 | 不直接推送主干 |
| 运维 / 实施 | 接收交付包；在客户现场部署与升级；回填部署回执 | 不修改代码与脚本 |
| 基线维护组 | 维护基线仓库；发布基线版本；评审各项目回流的经验与改进 | 不介入项目业务决策 |
| AI Agent | 起草规格与设计、编写代码与测试、执行门禁、生成报告 | **永远不做审批**，不写入任何确认记录 |

R = 执行，A = 最终负责/批准，C = 参与确认，I = 知会。

| 环节 | 工程师 | AI | PM | TL | 运维 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| 需求入库 | A | R | C | I | |
| 澄清与规格 | A | R | C（确认验收标准） | I | |
| 技术设计与计划 | R | R | | A | |
| 实现 | A | R | | | |
| 测试与业务验收 | A | R | | I | |
| 合并前复核与合并 | C | R（自审报告） | | A | |
| 发布打包 | C | R | I | A | I |
| 部署交付 | | | I | C | A |

## 3. 研发流程与交接规范

### 3.1 任务分级

分级由工程师提出、TL 认定，写在变更包或提交说明里。**有疑问时就高不就低。**

| 级别 | 判定条件（满足任一即升级） | 需要的产物 | 人工确认 |
| :--- | :--- | :--- | :--- |
| S 小改 | 不改表、不改接口、不改业务规则，单模块内修改 | 只需规范的提交说明 | 无（TL 合并时复核） |
| M 常规 | 单模块内新增功能或调整业务规则；只新增表或字段，不动已有字段 | 变更包：`proposal.md` + `spec-delta.md` + `tasks.md` + `acceptance.md` | PM 确认验收标准 |
| L 重大 | 修改或删除已有字段、处理存量数据；修改已发布接口；跨模块；涉及权限、安全、个人信息 | M 级全部产物 + `design.md` | PM 确认验收标准 + TL 审批设计 |

Bug 修复按影响面套用同一分级，额外要求先写复现测试。

### 3.2 标准流程

```
①需求入库 → ②澄清 → ③规格与验收标准确认 → ④技术设计与计划 → ⑤实现
    → ⑥测试与业务验收 → ⑦合并前复核与合并 → ⑧发布打包 → ⑨部署交付 → ⑩归档
```

| 环节 | 输入 | 主要活动 | 输出 | 完成标准 | 确认人 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| ① 需求入库 | 口头描述、文档、原型截图 | 工程师把原始材料存入仓库；AI 生成需求记录 | `docs/requirements/<REQ>/` 原始材料 + `intake.md` | 原始材料完整留存，口头需求有文字记录（谁、何时、说了什么） | 工程师 |
| ② 澄清 | `intake.md`、当前规格、术语表 | AI 对照现有规格找出歧义、遗漏、冲突，列出问题；工程师向 PM 求证 | `intake.md` 中的问答记录 | 所有问题有答案，或明确标记为"本期不做" | 工程师 |
| ③ 规格确认 | 澄清结论 | AI 起草变更提案与规格增量（业务规则 + 验收标准）；工程师把验收标准清单发给 PM 确认 | `proposal.md`、`spec-delta.md` | 每条验收标准可测试；PM 确认记录已写入 | **PM** |
| ④ 设计与计划 | 已确认规格、上下文索引 | AI 做影响分析，产出设计（L 级）与任务清单，列出修改范围 | `design.md`（L 级）、`tasks.md` | 修改范围、数据库与接口变更、存量兼容策略、验证命令齐全 | **TL**（L 级） |
| ⑤ 实现 | 设计与任务清单 | 先改契约与迁移脚本，再改代码；每完成一项更新 `tasks.md` | 代码、迁移脚本、接口契约 | 本地门禁通过；未超出修改范围 | — |
| ⑥ 测试与验收 | 验收标准、实现代码 | AI 编写自动化测试；工程师对不能自动化的标准做人工验证 | 测试代码、`acceptance.md` | 每条验收标准都有通过证据（自动化测试名或人工验证记录） | 工程师 |
| ⑦ 合并 | 功能分支、`acceptance.md` | AI 生成自审报告；TL 复核并执行完整校验后合并 | 主干上的合并提交 | 完整校验通过；复核意见已处理 | **TL** |
| ⑧ 发布打包 | 主干版本 | AI 汇总变更、配置项与迁移脚本，生成发布说明和部署手册 | `docs/releases/<版本>/` + 交付包 | 交付包结构符合第 9 章 | **TL** |
| ⑨ 部署交付 | 交付包 | 运维按手册部署或升级 | 部署回执 | 回执已登记到客户版本台账 | **运维** |
| ⑩ 归档 | 已发布的变更包 | 把规格增量合并进当前规格，变更包移入归档；把经验写入踩坑记录 | 更新后的 `docs/specs/`、`docs/context/pitfalls.md` | 当前规格与线上行为一致 | 工程师 |

### 3.3 需求变更

需求变更不是"改一下代码"，而是一个新的变更包：

1. 新建 `REQ`，在 `proposal.md` 中注明"变更自哪个能力、哪条业务规则"。
2. `spec-delta.md` 只写增量：新增、修改、删除了哪些规则和验收标准。
3. AI 必须先读该能力的**当前规格**和相关的已归档变更包，再做影响分析。设计必须说明对已有数据、已有接口、已有测试的影响。
4. 与已有测试语义冲突的地方，要在设计中逐条列出，由 TL 确认后才能修改这些测试。

这样无论隔多久、换哪个工程师或 AI 工具，看到的都是"当前完整规格 + 本次增量"，不会凭局部理解推翻已有设计。

### 3.4 PM 确认的记录方式

PM 不使用 Git，确认通过文档或即时通讯完成：

1. 工程师从 `spec-delta.md` 导出"业务规则与验收标准清单"发给 PM。
2. PM 回复确认或修改意见。
3. **工程师本人**在 `proposal.md` 的确认区登记：确认人、时间、方式（如"微信群""邮件"），并附原话或截图。

AI 不得填写确认区（见 6.6 节）。

## 4. 标准产物与模板

### 4.1 项目仓库中的文档结构

```
docs/
├── requirements/                 # 需求入库区：原始材料留存，只增不改
│   └── REQ-20261015-visitor-approval/
│       ├── raw/                  # 原始文档、原型截图、口头需求记录
│       └── intake.md             # 需求记录 + 澄清问答
├── specs/                        # 当前有效规格：按"能力"组织，始终代表系统现状
│   └── visitor-appointment/
│       └── spec.md
├── changes/                      # 进行中的变更包
│   ├── REQ-20261015-visitor-approval/
│   │   ├── proposal.md           # 变更提案：为什么改、改什么、分级、PM 确认记录
│   │   ├── spec-delta.md         # 规格增量：新增/修改/删除的业务规则与验收标准
│   │   ├── design.md             # 技术设计（L 级必需）：影响分析、数据库、接口、兼容策略
│   │   ├── tasks.md              # 任务清单：修改范围 + 带勾选框的步骤，兼作会话检查点
│   │   └── acceptance.md         # 测试与验收报告：逐条验收标准的通过证据
│   └── archive/                  # 已发布的变更包
├── context/                      # 给 AI 和新人的上下文索引
│   ├── glossary.md               # 术语表（业务名词中英对照）
│   ├── architecture.md           # 模块划分与依赖关系
│   ├── owners.md                 # 模块负责人
│   ├── db-schema.md              # [生成] 当前表结构摘要
│   └── pitfalls.md               # 踩坑记录
├── adr/                          # 架构决策记录
└── releases/
    ├── deployments.md            # 客户版本台账：哪个客户现场在什么版本
    └── v1.3.0/
        ├── release-notes.md
        └── deploy-guide.md
```

### 4.2 编号规则

| 对象 | 格式 | 示例 | 说明 |
| :--- | :--- | :--- | :--- |
| 需求 / 变更 | `REQ-YYYYMMDD-<英文短名>` | `REQ-20261015-visitor-approval` | 用日期加短名，多人并行时不会撞号；一个需求对应一个变更包 |
| 缺陷 | `BUG-YYYYMMDD-<英文短名>` | `BUG-20261016-passcode-expire` | S 级缺陷可以不建目录，只写在提交说明里 |
| 验收标准 | `AC-<能力>-<两位序号>` | `AC-visitor-appointment-07` | 在能力内递增，归档后不再复用 |
| 版本 | `vMAJOR.MINOR.PATCH` | `v1.3.0` | 项目交付版本 |

### 4.3 追溯链路

```
需求原始材料 ─► intake.md ─► proposal.md / spec-delta.md（AC 编号）
                                  │
                design.md / tasks.md ─► 提交说明（Refs: REQ-xxx）
                                  │
          测试名包含 AC 编号 ─► acceptance.md ─► release-notes.md ─► 部署回执
```

任意一行代码都能通过 `git log` 找到对应需求；任意一条验收标准都能找到对应的测试和通过证据。

### 4.4 模板要点

所有模板放在模板的 `docs/_templates/` 下（创建项目时随项目生成，属于基线托管文件），每个模板都附有一份填写完整的示例（见 10.1 节的 `examples/`）。示例是给 AI 做参照的，比文字说明更有效。

**`spec.md`（当前规格）**：能力概述、术语、角色与权限、数据对象与关键字段、状态与流转、业务规则（编号 `BR-<能力>-NN`）、验收标准（编号 `AC-<能力>-NN`，采用"前提 / 操作 / 结果"三段式写法）、不在范围内的内容。

**`proposal.md`**：背景与目标、变更类型（新增 / 修改 / 删除）、任务分级与理由、涉及的能力、对用户可见的影响、PM 确认区（仅限工程师填写）。

**`design.md`**：影响分析（表、接口、模块、页面、已有测试）、数据库变更与存量兼容策略、接口变更与兼容性、方案取舍、风险与回退方式、TL 审批区（仅限 TL 填写）。

**`tasks.md`**：

```markdown
## 修改范围
- 允许修改：backend/modules/visitor/**，contracts/openapi/visitor.yaml，db/migration/**/V202610151400__visitor_*.sql
- 禁止修改：其他模块、基线托管文件

## 任务
- [x] T1 新增迁移脚本（PostgreSQL / 达梦两份）  验证：./scripts/verify.sh db
- [ ] T2 更新接口契约并生成前端客户端          验证：cd frontend && pnpm gen:api && pnpm typecheck
- [ ] T3 后端实现审批流转                      验证：./scripts/verify.sh backend
      备注：存量预约 approval_required=false，不得拦截其核销
```

**`acceptance.md`**：逐条列出验收标准，每条写明验证方式（自动化 / 人工）、证据（测试类与方法名，或人工操作步骤加截图）、结果；末尾附完整校验的执行记录。

## 5. 工程约定

### 5.1 项目结构约定

```
<项目代号>/
├── AGENTS.md / CLAUDE.md / .cursor/rules/   # [生成] AI 工具入口
├── .ai/
│   ├── rules/                 # [基线托管] 规则源
│   ├── skills/                # [基线托管] 标准 Skills
│   └── project/               # [项目自有] 项目专属规则
├── .baseline/                 # [基线托管] 基线版本号与同步元数据
├── docs/                      # [项目自有] 见第 4 章
├── contracts/openapi/         # [项目自有] 接口契约（前后端唯一事实源）
├── backend/                   # [项目自有] Maven 多模块
│   ├── app/                   # 启动与装配
│   └── modules/<模块>/        # 业务模块
├── frontend/                  # [项目自有] pnpm 工作区
│   ├── apps/admin/            # 管理后台
│   ├── apps/screen/           # [可选] 大屏可视化
│   └── packages/api-client/   # [生成，不入库] 由契约生成
├── db/migration/              # [项目自有] 按方言分目录，见 5.4 节
├── deploy/                    # [项目自有] 本地环境、打包脚本、部署模板
└── scripts/                   # [基线托管] verify、gen-api、db-schema、new-module 等
```

**后端模块内部结构**（统一包名 `com.dsmeta.<项目代号>.<模块>`）：

| 包 | 内容 | 约束 |
| :--- | :--- | :--- |
| `api` | 提供给其他模块调用的接口与 DTO | 其他模块**只能**依赖这个包 |
| `web` | Controller、请求与响应对象 | 不写业务分支，不注入 Repository，不加事务 |
| `service` | 业务编排与事务边界 | 事务只在这一层 |
| `domain` | 实体、仓储接口、状态枚举、领域规则 | 不依赖 `web` |
| `infra` | 外部系统适配、复杂查询实现 | 不被 `web` 直接依赖 |

模块边界由 Spring Modulith 或 ArchUnit 的通用规则检查，规则按包名模式写一次即可覆盖所有模块，新增模块不用改规则。新模块统一用 `scripts/new-module.sh <模块名>` 生成，不让 AI 手工搭目录。

### 5.2 技术栈分级

| 级别 | 含义 |
| :--- | :--- |
| 强制 | 所有项目必须使用，版本由骨架锁定 |
| 推荐 | 遇到对应场景时的默认选择，Skills 按它生成代码 |
| 画像 | 特定类型项目启用（信创画像、大屏画像） |
| 需评审 | 引入清单以外的技术，需在项目 `docs/adr/` 写决策记录并经基线维护组同意 |

| 领域 | 选型 | 级别 |
| :--- | :--- | :--- |
| 后端语言与框架 | Java（LTS）、Spring Boot（当前受官方支持的稳定版） | 强制 |
| 持久层 | Spring Data JPA（Hibernate） | 强制 |
| 对象映射、校验 | MapStruct、Jakarta Validation | 强制 |
| 数据库 | PostgreSQL；信创画像：达梦、人大金仓 | 强制 / 画像 |
| 数据库迁移 | Flyway（达梦支持情况待验证，见 11.1 节） | 强制（待验证） |
| 缓存 | Redis 协议兼容实现（Redis / Valkey，按许可证评估） | 推荐 |
| 对象存储 | S3 协议，代码只依赖 S3 接口，具体产品按交付环境选择 | 推荐 |
| 前端 | Vue 3（`<script setup lang="ts">`）、TypeScript、Vite、pnpm | 强制 |
| 前端组件与状态 | Element Plus、Pinia、Vue Router | 强制 |
| 接口契约与代码生成 | OpenAPI 3.x；后端用 openapi-generator 生成接口，前端用 Orval 生成客户端 | 强制 |
| 测试 | JUnit 5、Testcontainers、Vitest、Playwright（只覆盖核心主流程） | 强制 |
| 大屏可视化 | Three.js、CesiumJS、ECharts | 画像 |
| 部署 | Docker 镜像 + Docker Compose；信创画像需支持 ARM 架构镜像 | 强制 |

**版本原则**：手册只写主版本和原则，具体版本由骨架的 BOM 与 `package.json` 锁定；基线维护组每季度评审一次升级。Spring Boot 主版本的选择必须先通过信创数据库方言兼容性验证（见 11.1 节），不能为追新而牺牲信创可用性。

**JPA 使用约定**（AI 最容易出问题的地方）：

- `spring.jpa.hibernate.ddl-auto=validate`，**禁止** `update`。表结构只由迁移脚本修改；实体与表不一致时应用启动即失败，测试阶段就能发现。
- `spring.jpa.open-in-view=false`。
- 关联默认 `LAZY`；不跨模块建立实体关联，跨模块只存 ID；不使用级联删除。
- 列表查询必须说明如何避免 N+1（`@EntityGraph` 或专用查询）。
- 原生 SQL 只允许放在 `infra` 包，并且需要为每种启用的方言提供实现或证明可移植。

### 5.3 编码风格

原则：**风格由工具定义，文档只写工具管不了的内容。**

| 内容 | 载体 |
| :--- | :--- |
| 格式 | `.editorconfig`、Spotless（Java）、Prettier（TS / Vue） |
| 静态规则 | Checkstyle 精简规则集、ESLint（禁止 `any`、禁止未使用变量等） |
| 架构边界 | Spring Modulith / ArchUnit 测试 |
| 命名与写法 | 手册中一页命名约定（类名后缀、接口路径、枚举、常量）+ 正反示例 |

以上配置文件都属于基线托管文件，随基线同步，项目内不允许修改。

### 5.4 数据库演进规范

**目录与命名**

```
db/migration/
├── postgresql/V202610151400__visitor_add_approval.sql
└── dm/V202610151400__visitor_add_approval.sql        # 信创画像启用的方言，同名同版本
```

- 文件名：`V<年月日时分>__<模块>_<英文描述>.sql`，用时间戳避免多人并行撞号。
- 每个启用的方言目录下，迁移文件必须一一对应（由门禁检查）。
- 已合并到主干的迁移脚本**只读**，任何修改都必须新增脚本（由门禁检查校验和）。
- 测试数据放在 `src/test/resources`，不进生产迁移目录。

**可移植约定**

- 标识符：小写加下划线，表名 `<模块>_<实体>`，不用数据库保留字。
- 主键：`BIGINT`，由应用生成；**在 JSON 中以字符串传输**，防止前端精度丢失。
- 标准字段：`id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`version`（乐观锁）、`deleted`（逻辑删除标记）。时间统一按 UTC 存储。
- 公共约定只使用可移植类型；`JSONB`、PostGIS、pgvector 等专有特性只能在画像范围内、明确不需要信创的模块中使用。
- 各方言的类型映射表放在手册附录，在信创验证（11.1 节）后补全。

**变更安全规则**

| 操作 | 要求 |
| :--- | :--- |
| 新增表、新增可空字段、新增带默认值的字段 | M 级即可 |
| 新增非空字段 | 用默认值让存量数据落到兼容值，新代码显式写入新值；**不依赖数据库默认值表达业务状态** |
| 修改字段类型、重命名、删除字段或表 | L 级，按"扩展 → 迁移 → 收缩"分多个版本完成，删除必须在确认无代码引用的后续版本中进行 |
| 存量数据回填 | L 级；大表分批执行；在 `design.md` 中写明数据量估算与执行时长 |
| 大表加索引 | 使用不锁表的方式（如 PostgreSQL 的 `CONCURRENTLY`），单独成脚本 |

**多客户版本升级**：私有化客户停留在不同版本，hotfix 脚本可能比主干上更新的脚本时间戳更早。规则：

1. 每次发布前，`verify` 必须执行**升级路径测试**：针对客户版本台账中每个在用版本，先迁移到该版本，再升级到目标版本，全部成功才能发布。
2. 每个迁移脚本只能依赖本模块此前的脚本，保证乱序执行也安全。

### 5.5 接口契约规范

- `contracts/openapi/` 是前后端唯一事实源：先改契约，再生成代码，再实现。
- 后端 Controller 实现由契约生成的接口，字段不一致直接编译失败；前端客户端由契约生成，不入库、不手改。
- 成功响应直接返回业务对象，错误响应采用 RFC 9457 ProblemDetail 并扩展 `code`、`traceId`（见项目内 `docs/adr/0001`）；错误码分段、分页参数（页码从 1 开始，每页上限 200）在骨架中给出实现。
- 已发布接口只允许兼容性扩展（新增可选字段、新增接口）；破坏性变更按 L 级处理，并通过契约对比工具检查。

## 6. AI 协作规范

### 6.1 规则只维护一份，编译生成各工具的配置

```
.ai/rules/*.md（规则源，带适用范围元数据）
        │  scripts/build-ai-config.sh
        ├──► AGENTS.md            # 通用入口（Codex 等工具读取），不超过 150 行：项目概况、红线、路由表、常用命令
        ├──► CLAUDE.md            # 引用 AGENTS.md，再补充 Claude Code 专属说明
        └──► .cursor/rules/*.mdc  # 按目录或文件类型自动挂载
.ai/skills/<名称>/SKILL.md ──► 同步到各工具的 Skills 发现目录（目录位置以各工具官方文档为准，由脚本维护）
```

- 生成的文件头部标注"由基线生成，禁止手改"，门禁会检查生成结果与规则源是否一致。
- 项目专属规则写在 `.ai/project/`，一起参与编译，但同步基线时不会被覆盖。

### 6.2 规则写法

为了让能力较弱的私有模型也能执行到位：

- 每条规则一句话，用"必须 / 禁止"开头，并附一个正例和一个反例。
- 规则按"读什么文件 → 做什么 → 运行什么命令验证"的顺序写。
- 能用脚本生成的（新建模块、接口客户端、表结构摘要），规则里只写"运行某个脚本"，不让 AI 手写。
- 凡是能由门禁检查的规则，规则文档里只保留一句话，并写明"违反会被哪个检查拦截"。

### 6.3 标准 Skills 与流程环节的对应

| Skill | 对应环节 | 输入 | 输出 | 第一版 |
| :--- | :--- | :--- | :--- | :---: |
| `req-intake` 需求入库与澄清 | ①② | 原始材料、当前规格、术语表 | `intake.md`、澄清问题 | ✓ |
| `spec-change` 规格起草 | ③ | 澄清结论、当前规格 | `proposal.md`、`spec-delta.md` | ✓ |
| `change-design` 影响分析与计划 | ④ | 规格、上下文索引 | `design.md`、`tasks.md` | ✓ |
| `db-migration` 数据库迁移 | ⑤ | 设计、现有表结构 | 各方言迁移脚本 | ✓ |
| `api-contract` 接口契约 | ⑤ | 设计、现有契约 | 契约文件、生成的代码 | |
| `implement` 前后端实现 | ⑤ | 任务清单、契约 | 代码 | ✓ |
| `test-accept` 测试与验收 | ⑥ | 验收标准、实现 | 测试、`acceptance.md` | ✓ |
| `self-review` 自审 | ⑦ | 改动内容、变更包 | 自审报告 | ✓ |
| `bugfix` 缺陷修复 | ⑤⑥ | 缺陷描述、日志 | 复现测试、修复、踩坑记录 | |
| `release-pack` 发布打包 | ⑧ | 版本范围 | 发布说明、部署手册、交付包 | |
| `archive` 归档 | ⑩ | 已发布变更包 | 合并后的当前规格 | |

每个 Skill 统一包含：适用条件、必须读取的文件、步骤、输出模板、完成标准、必须停下来请人确认的情形。

### 6.4 上下文与会话管理

- **上下文入口固定**：AI 先读 `AGENTS.md`，再按路由表读 `docs/context/` 和当前变更包，不扫描全仓。
- **表结构摘要由真实数据库生成**：在测试容器中执行全部迁移后导出，保证与实际一致。
- **一个会话只做一个环节**：完成一个环节（如规格确认、某项任务）后，把状态写进 `tasks.md`，再开新会话继续。新会话只需要"读取变更包 `<REQ>` 的 `tasks.md`，从第一个未完成任务继续"。
- 换工具、换人、隔天继续都用同一种方式恢复上下文。

### 6.5 AI 必须停下来请人确认的情形

1. 当前任务没有变更包，或者 L 级设计尚未经 TL 审批。
2. 需要修改 `tasks.md` 修改范围以外的文件。
3. 需要删除或修改已有字段、删除表、清空数据、修改已合并的迁移脚本。
4. 需要对已发布接口做破坏性修改。
5. 需要引入骨架和技术栈清单以外的依赖。
6. 已有测试失败，且原因是业务规则发生了变化。
7. 同一问题连续修复 3 次仍失败。
8. 需求描述与当前规格冲突。

规则要求 AI 在这些情形下输出固定标记 `[需要人工决策]`，并说明原因与可选方案。

### 6.6 AI 不能做的事

- 不填写任何确认或审批区（PM 确认区、TL 审批区、部署回执）。
- 不删除测试、不跳过测试、不降低断言强度来让校验通过。
- 不修改基线托管文件。
- 不推送主干分支。

### 6.7 项目密级与 AI 使用

| 密级 | 判定 | 可用模型与工具 | 额外要求 |
| :--- | :--- | :--- | :--- |
| 普通 | 内部或商业项目，客户无特殊要求 | 部门批准的云端 AI 工具 | 不提交密钥和客户真实数据 |
| 受限 | 客户要求代码不出境或不出公司 | 国内合规云服务或私有化模型 | 工具配置为指定的模型服务 |
| 涉密 | 合同或客户明确要求代码不离开内网 | **仅限**私有化部署模型，以及能接入私有模型的工具 | 开发环境与外网隔离；禁止使用云端 AI 工具打开该仓库 |

通用要求：

- 项目密级写在 `AGENTS.md` 顶部和 `.baseline/` 元数据中，由 TL 在立项时确定。
- 密钥、证书、生产配置一律不入库；骨架自带密钥扫描钩子和各工具的忽略文件。
- AI 的运行环境里不放生产数据库账号；需要真实数据排查时，只使用脱敏样本。
- 身份证号、手机号等个人信息字段，按手册规定加密存储、脱敏展示；需要查询时另存哈希索引列。

### 6.8 多人与多 Agent 并行

- 默认一个工程师驱动一个主 Agent 完成整个变更包；独立的自审 Agent 只在合并前使用。
- 需要并行（例如前后端同时开发）时：先合并契约和迁移脚本，再分别在独立的 Git 工作树中开发，`tasks.md` 中为每个并行任务写明互不重叠的修改范围。
- 模块负责人登记在 `docs/context/owners.md`；修改他人负责的模块，需要在变更包中注明并告知负责人。

## 7. 质量门禁

### 7.1 四层门禁（适配裸 Git）

| 层次 | 时机 | 检查内容 | 能否被绕过 |
| :--- | :--- | :--- | :--- |
| ① 编辑时 | 保存、AI 生成后 | 格式化 | — |
| ② 本地提交钩子 | `git commit` | 格式、Lint、密钥扫描、基线托管文件与已合并迁移脚本是否被修改、提交说明格式 | 能（`--no-verify`） |
| ③ 本地推送钩子 | `git push` | 编译、单元测试、架构规则、迁移脚本方言对应、AI 配置与规则源是否一致 | 能 |
| ④ TL 合并前复核 | 合并到主干前 | `./scripts/verify.sh full`：全部测试（含 Testcontainers）、升级路径测试、契约兼容对比、测试删除检查；结果写入 `acceptance.md` | **不能**，这是真正的关口 |
| ⑤ 服务端钩子（建议） | 推送到服务器 | 只允许 TL 推送主干；拒绝无需求编号的提交；拒绝修改已合并的迁移脚本 | 不能 |

- 钩子通过 `scripts/setup.sh` 一键安装（设置 `core.hooksPath`），新成员克隆后必须执行。Windows 用 `scripts\setup.cmd`，钩子本身仍由 Git 自带的 sh 调用 Python。
- 裸 Git 服务器上可以直接配置服务端钩子（需要服务器管理员权限）；需要按分支控制推送权限时，可以加一层 Gitolite。
- 将来引入 Gitea、Jenkins 等平台时，把第 ④ 层原样迁移到 CI 即可，规则不变。

### 7.2 阻断与告警

| 检查 | 处置 |
| :--- | :--- |
| 格式、Lint、类型检查、编译 | 阻断 |
| 架构边界、实体与表结构一致（`ddl-auto=validate`） | 阻断 |
| 迁移脚本：方言对应、已合并脚本未被修改、升级路径测试 | 阻断 |
| 接口契约的破坏性变更（未在 L 级设计中声明） | 阻断 |
| 全部测试通过，且没有被删除或跳过的测试 | 阻断（确需删除时在 `design.md` 中说明并由 TL 认可） |
| 密钥泄露、高危依赖漏洞 | 阻断 |
| 每条验收标准都有通过证据 | 阻断（TL 复核） |
| 新增代码覆盖率、方法复杂度、文件行数 | 告警，第一阶段只统计不设阈值 |

### 7.3 没有专职测试时的测试要求

- 验收标准是测试的依据：每条 `AC` 至少对应一个自动化测试（测试名包含 AC 编号），或者一条人工验证记录（步骤加截图）。
- 业务验收由负责工程师完成，逐条填写 `acceptance.md`；TL 合并时抽查。
- 测试分层：领域规则用单元测试；数据库与接口用 Testcontainers 集成测试；只为核心主流程写端到端测试。
- 信创画像项目：集成测试至少在 PostgreSQL 和一种启用的国产数据库上各跑一次。

## 8. Git 协作

### 8.1 分支

| 分支 | 用途 | 规则 |
| :--- | :--- | :--- |
| `main` | 主干，随时可发布 | 只有 TL 能合并和推送 |
| `feat/<REQ>`、`fix/<BUG>` | 功能与修复分支 | 生命周期尽量不超过一周；大需求拆成多个变更包 |
| `release/<主.次>` | 已交付给客户的版本线 | 只接收 hotfix，修复后必须合回主干 |

- 不为单个客户建长期分支，客户差异通过配置和功能开关实现。
- 尚未完成的功能用功能开关隐藏，保证主干随时可以发布。

### 8.2 合并流程（无 PR）

1. 工程师把功能分支变基到最新主干，本地完整校验通过后推送到服务器。
2. 工程师通知 TL，并附上变更包路径。
3. TL 拉取分支，阅读变更包和改动（可以使用 `self-review` Skill 辅助），执行 `./scripts/verify.sh full`。
4. 有意见时，在变更包的 `design.md` 或 `acceptance.md` 末尾写复核意见，由工程师修改后再次提交。
5. 通过后，TL 以 `--no-ff` 方式合并并推送主干。合并提交的提交人就是复核记录。

### 8.3 提交说明

```text
feat(visitor): 新增访客预约审批流

- 新增迁移脚本 V202610151400，存量预约默认免审
- 实现审批通过与驳回接口

Refs: REQ-20261015-visitor-approval
AI-Assisted: claude-code
```

- 类型使用 `feat`、`fix`、`refactor`、`test`、`docs`、`chore`；描述用中文。
- `Refs` 必填（S 级也要关联需求或缺陷编号）；使用了 AI 时写明工具。
- 提交说明格式由提交钩子检查。

## 9. 交付与部署协作

### 9.1 研发交给运维的交付包

```
<项目>-v1.3.0/
├── images/                 # 镜像离线包（信创画像需包含 ARM 架构）
├── db/                     # 本版本的迁移脚本（按方言），或说明随应用自动执行
├── config/                 # 配置模板：列出全部配置项、含义、默认值、是否必填
├── release-notes.md        # 面向运维和客户：新增功能、修复、已知问题
├── deploy-guide.md         # 全新部署步骤
├── upgrade-guide.md        # 从每个在用版本升级的步骤、预计停机时间、回退方式
└── checksums.txt
```

- 交付包由 `release-pack` Skill 结合打包脚本生成，结构固定。
- 生产环境迁移作为独立步骤执行，不随应用启动自动执行；执行前必须备份数据库。

### 9.2 部署回执与客户版本台账

运维每次部署或升级后回填回执：客户现场、版本、时间、结果、遇到的问题。由工程师或 TL 登记到 `docs/releases/deployments.md`。这份台账有两个用途：

1. 作为 5.4 节升级路径测试的版本清单。
2. 客户现场出问题时，快速知道对方处于什么版本。

### 9.3 信创环境

- 骨架同时提供 PostgreSQL 与国产数据库的配置示例，切换数据库只改配置。
- 镜像构建支持 x86 与 ARM 两种架构。
- 客户要求部署到国产应用服务器时，骨架提供 WAR 打包方式作为可选项。

## 10. 基线仓库本身

### 10.1 目录结构

```
ai-native-engineering/
├── README.md                   # 基线是什么、怎么用、怎么创建新项目
├── CHANGELOG.md                # 每个基线版本的变化与升级注意事项
├── copier.yml                  # 创建项目时的问题、项目自有文件清单
├── bin/                        # new-project（.sh/.cmd/.ps1，创建项目）、selftest.sh（基线自测，维护者）
├── handbook/                   # 研发规范手册：本方案全文 + 按角色的操作指南
├── template/                   # 项目模板 = 空骨架 + 基线托管文件
│   ├── .ai/  .baseline/  .githooks/  scripts/
│   ├── docs/_templates/        # 产物模板，以及填写完整的示范变更包 examples/
│   ├── backend/  frontend/  db/  deploy/  contracts/
│   └── 各类格式化与 Lint 配置
├── tools/server-hooks/         # 裸 Git 服务端钩子（规则编译与门禁脚本在 template/scripts/ 下，随项目分发）
└── proposals/                  # 各项目对基线的改进提案（替代 issue 系统）
```

### 10.2 创建项目与同步升级

推荐使用 Copier（开源的项目模板工具），它支持在模板升级时做三方合并，不需要自研命令行工具：

| 操作 | 命令 | 效果 |
| :--- | :--- | :--- |
| 创建项目 | `copier copy <基线仓库> <项目目录>` | 交互填写项目代号、密级、画像（信创、大屏），生成项目 |
| 同步升级 | `copier update --vcs-ref v1.4.0` | 更新基线托管文件；项目自有文件不受影响；有冲突时提示人工处理 |

- 骨架代码（`backend/`、`frontend/` 的源码）只在创建时复制，之后归项目所有，同步时不覆盖。
- 基线托管文件清单写在 `copier.yml` 中，门禁据此检查项目内是否手改了这些文件。
- 运行环境需要 Python 和 Git；离线环境可以提前准备安装包。

### 10.3 基线版本

- 采用语义化版本：**主版本**表示流程或规范有不兼容变化，需要培训；**次版本**表示新增规则、Skills 或检查；**修订版本**表示修正错误。
- 项目在 `.baseline/` 中记录当前基线版本。要求活跃项目不落后于最新次版本超过两个版本。

### 10.4 维护组织与回流

- **基线维护组**：1 名架构负责人，加后端、前端、大屏可视化、AI 协作各 1 名兼职负责人。
- **节奏**：每月发布一个次版本；紧急修正随时发布修订版本。
- **回流**：各项目把有价值的踩坑记录、Skill 改进、规则补充写成 `proposals/` 下的提案；维护组每月评审，采纳的内容进入下一个版本。
- **度量**（第一阶段只采集，不设考核）：需求从规格确认到交付的周期、TL 复核一次通过的比例、上线后缺陷数、活跃项目的基线版本分布。试点开始前，先采集现有项目的同类数据作为对照。

## 11. 落地路线与第一版范围

### 11.1 第 0 阶段：关键验证（1 ~ 2 周）

在写规范之前，先验证这几个会推翻设计的问题：

| 验证项 | 通过标准 | 不通过时的备选 |
| :--- | :--- | :--- |
| 选定的 Spring Boot / Hibernate 版本对达梦、人大金仓的方言支持 | 骨架实体能在两种国产数据库上 `validate` 通过并完成增删改查 | 退回到能兼容的最新版本 |
| Flyway 对达梦、人大金仓的支持 | 能执行、记录、校验迁移 | 改用 Liquibase，或在骨架中提供轻量迁移执行器 |
| 私有化模型能否按规则和 Skills 完成一个 M 级变更包 | 产出能通过门禁 | 简化规则与 Skills，增加脚本化生成的比例 |
| 三种 AI 工具能否读取同一套生成配置和 Skills | 对同一任务的产出结构一致 | 调整编译脚本的输出格式 |

### 11.2 第 1 阶段：第一版基线与试点（3 ~ 4 周）

第一版必须包含：

1. 规范手册：总则、角色职责、研发流程、产物规范、工程约定、AI 协作、门禁、Git 协作（交付部署章节可以先写简版）。
2. 产物模板与一个完整的示范变更包。
3. 规则源、编译脚本、7 个第一版 Skills（6.3 节中打勾的项）。
4. 门禁：提交钩子、推送钩子、`verify.sh`（含升级路径测试的基础能力）。
5. 空骨架：后端单模块示例、前端管理后台、本地开发环境、`new-module.sh`、`pnpm gen:api`。
6. Copier 模板与创建项目流程。

试点：选一个新建的常规业务管理系统，由 3 ~ 5 人小组全程按基线交付第一个里程碑。

### 11.3 第 2 阶段：扩展（4 周）

- 补齐其余 Skills（接口契约、缺陷修复、发布打包、归档）。
- 信创画像、大屏可视化画像。
- 交付包与部署回执流程；`copier update` 同步流程实际演练一次。
- 第二、第三个项目接入（至少包含一个信创项目和一个大屏项目）。

### 11.4 第 3 阶段：推广与治理（持续）

- 全员培训：按角色分别培训工程师、TL、产品经理（只讲 3.4 节的确认方式）、运维（只讲第 9 章）。
- 启动月度回流评审。
- 评估引入轻量代码平台（如 Gitea）和 CI，把第 ④ 层门禁迁移到服务端。

### 11.5 第一版不做

- 不做公共业务模块（用户权限、组织机构、工作流等）。
- 不做公共技术 SDK 和三维可视化引擎封装。
- 不做 Web 管理平台、多 Agent 调度平台、外部知识库问答系统。
- 不对接需求管理系统。
- 不引入微服务基础设施。
