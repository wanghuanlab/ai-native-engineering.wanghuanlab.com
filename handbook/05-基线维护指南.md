# 基线维护指南

## 仓库结构

| 路径 | 内容 |
| :--- | :--- |
| `copier.yml` | 创建项目时的问题；`_skip_if_exists` 列出项目自有文件（同步时不覆盖） |
| `template/` | 项目模板。`.jinja` 后缀的文件会渲染变量，其余原样复制 |
| `template/.baseline/managed-files.txt` | 基线托管文件，项目内修改会被提交钩子拦截 |
| `template/.ai/` | AI 规则与 Skills 源文件 |
| `template/scripts/` | 门禁、脚手架、发布脚本 |
| `bin/selftest.sh` | 自测 |
| `tools/server-hooks/` | 服务端钩子 |
| `proposals/` | 改进提案 |

## 文件归属

| 类型 | 例子 | 同步基线时 |
| :--- | :--- | :--- |
| 基线托管 | `scripts/**`、`.ai/rules/**`、`.ai/skills/**`、`docs/_templates/**`、`.githooks/**`、Lint 配置 | 直接覆盖；项目内不能改 |
| 项目自有 | 业务源码、`contracts/`、`db/`、`docs/` 中的项目文档、`.ai/project/` | 不覆盖 |
| 共同维护 | `backend/pom.xml`、`frontend/package.json`、`copier.yml` 中未列出的其他文件 | Copier 三方合并，冲突时人工处理 |

新增模板文件时，先判断它属于哪一类，并同步更新 `managed-files.txt` 或 `copier.yml` 的 `_skip_if_exists`。

## 修改规则或 Skill

1. 规则写在 `template/.ai/rules/<编号>-<名称>.md`，文件头必须有 `id`、`title`、`scope`（`always` / `glob` / `requested`）、`summary`，`glob` 规则还要有 `globs`。
2. `always` 规则会全文进入 `AGENTS.md`，要克制：`AGENTS.md` 超过 150 行时编译失败。
3. 写规则要写"做什么、不做什么、怎么验证"，不写原理和背景。

## 发布基线版本

```bash
bin/selftest.sh all          # 三种画像全部通过（需要 Docker，约 5 分钟）
# 更新 CHANGELOG.md：变化、项目升级时需要注意的事项
git commit -am "chore: 发布 v0.2.0" && git tag -a v0.2.0 -m v0.2.0 && git push --follow-tags
```

版本号：主版本表示流程或规范有不兼容变化（需要培训）；次版本表示新增规则、Skills 或检查；修订版本表示修正错误。

`copier update` 依赖基线仓库的 Git 标签。项目里 `.baseline/copier-answers.yml` 的 `_src_path` 必须是团队能访问的 Git 地址（`https://`、`ssh://`、`git@`、`file://` 或 `git+` 前缀），不能是某台机器的目录。`bin/new-project` 在创建时写入这个地址，并固定 `_commit` 对应的标签或提交。

来源按这个顺序决定：

1. `--source`，或环境变量 `BASELINE_SOURCE`
2. 否则使用基线仓库的 `origin`，并去掉 `https://用户:令牌@` 里的凭据

引用按这个顺序决定：

1. 位置参数里的版本标签、`--ref` / `--vcs-ref`，或环境变量 `BASELINE_REF`
2. 否则，若当前提交正好有标签，用该标签
3. 否则用当前提交的完整哈希，并提示它必须已经推送到远端

`scripts/sync-baseline` 在调用 Copier 之前会检查来源：本机路径直接拒绝；`git ls-remote` 失败或远端没有这个标签/提交时，说明原因后退出，不改文件。要用新地址替换项目里记录的旧路径时，加上 `--source`。地址有变化时，脚本会先单独提交 `.baseline/copier-answers.yml`（工作区必须干净，Copier 拒绝在脏目录上更新）。

`bin/selftest.sh source` 用一个带 `v0.1.0` 和 `v0.2.0` 两个标签的本地 Git 仓库充当远端（`git+file://`），创建项目后再执行一次真实的 `copier update`。`selftest.sh` 的 `generate` 仍把本地检出目录交给 Copier，这样未提交的模板改动能进入画像测试；那条路径不代表团队创建项目的方式。

## 开发者命令的平台

门禁和脚手架的逻辑在 Python 3.10+（`template/scripts/*.py` 与 `scripts/lib/`）。每个开发者命令有三个薄入口：

| 平台 | 入口 |
| :--- | :--- |
| macOS / Linux | `scripts/<名>.sh`、`bin/new-project.sh` |
| Windows cmd | `scripts\<名>.cmd`、`bin\new-project.cmd` |
| Windows PowerShell | 同名 `.ps1` |

`.sh` 只查找 `python3`、`python` 或 `py -3` 然后执行，兼容 macOS 自带的 Bash 3.2。Windows 上优先 `py -3`。`.cmd` / `.ps1` 不复制业务判断。

Git 钩子（`.githooks/`）在 Windows 上由 Git for Windows 自带的 sh 启动，因此保持 POSIX sh，再交给 Python。它们不调用 `sed`、`find`、`uname` 等只有某一侧才有的工具。换行由仓库根和 `template/.gitattributes` 约定：一般文本用 LF，`*.cmd`、`*.bat`、`*.ps1` 用 CRLF。后端构建在 Windows 上走 `mvnw.cmd`，`pnpm` / `npm` 经 `cmd /c` 启动。

以下部分保持原样，并写明原因：

| 部分 | 原因 |
| :--- | :--- |
| `tools/server-hooks/pre-receive` | 装在 Git 服务器上，不在开发者的 Windows 电脑上运行 |
| `bin/selftest.sh` | 维护者在发布前于 macOS / Linux 跑的总闸，会生成项目并调用 Docker；不是日常开发命令 |
| `db-schema`、`upgrade-path` 的数据库 | 需要 Docker（Windows 上是 Docker Desktop）。没有 Docker 时 Python 会说明缺什么，而不是静默跳过 |
| `release-pack --images` | 需要 Docker Buildx 打 linux/amd64 与 linux/arm64 镜像 |
| `.cmd` 的参数 | 含 `&`、`!` 等 cmd 特殊字符时，延迟展开可能拆错参数；这种参数改用 `.ps1` 或 Git Bash |

## 处理改进提案

各项目把踩坑经验、Skill 改进写成 `proposals/<日期>-<短名>.md`（格式见 `proposals/README.md`）。维护组每月评审一次，采纳的进入下一个次版本，在 `CHANGELOG.md` 中注明来源项目。
