# 技术负责人指南

你是项目里唯一能合并 main 的人。基线中真正不可绕过的关口是你执行的合并前复核。

## 创建项目

```bash
# 在基线仓库中。Windows 用 bin\new-project.cmd，随后 scripts\setup.cmd 与 scripts\verify.cmd
bin/new-project.sh ~/work/park v0.1.0
cd ~/work/park
./scripts/setup.sh && ./scripts/verify.sh quick
git add -A && git commit -m "chore(baseline): 初始化项目" -m "Refs: BASELINE-v0.1.0"
git remote add origin <裸仓库地址> && git push -u origin main
```

创建时需要回答：项目代号、名称、包名前缀、技术负责人（Git 用户名，多人用逗号分隔）、密级、是否信创及数据库、是否需要大屏、是否保留示例模块。

`new-project` 把基线来源写成团队可访问的 Git 地址，并固定到标签或提交。默认使用基线仓库的 `origin`（去掉地址中的令牌）。换地址用 `--source <Git URL>` 或环境变量 `BASELINE_SOURCE`；换标签或提交用位置参数、`--ref` 或 `BASELINE_REF`。来源必须能被 `git ls-remote` 访问，并且上面能找到这个引用。不要把本机目录传给 Copier，否则别的机器无法同步。

建议在 Git 服务器上安装服务端钩子（需要服务器管理员）：

```bash
cp <基线>/tools/server-hooks/pre-receive <仓库>.git/hooks/ && chmod +x <仓库>.git/hooks/pre-receive
git --git-dir=<仓库>.git config hooks.techleads "wanghuan lisi"
```

## 日常职责

| 时机 | 做什么 |
| :--- | :--- |
| 需求入库后 | 认定任务级别（S / M / L），拿不准取高 |
| L 级设计完成 | 审阅 `design.md`，重点：存量数据、在用版本的升级影响、接口兼容、已有测试的语义冲突；在审批区签字 |
| 工程师通知合并 | 按 `docs/context/collaboration.md`「合并前复核」执行，`./scripts/verify.sh full` 必须通过 |
| 测试被删除或减少 | `verify.sh full` 会拦截。确属业务变化且已在 `design.md` 说明时，执行 `ALLOW_TEST_CHANGE=<REQ> ./scripts/verify.sh full` |
| 发布 | 让 AI 执行 `release-pack` 起草文档；审阅后打标签，执行 `./scripts/release-pack.sh <版本> [--images]`（Windows：`scripts\release-pack.cmd`） |
| 部署回执 | 登记到 `docs/releases/deployments.md`，更新「在用版本」（这是升级路径测试的版本清单） |
| 基线发布新版本 | `./scripts/sync-baseline.sh <版本>`。记录的来源若是旧的本机路径，或要改用另一个 Git 地址，加上 `--source <Git URL>`。检查改动、`verify.sh full` 通过后提交 |

## 复核时重点看什么

1. PM 确认记录是人填的，内容与 `spec-delta.md` 一致。
2. 每条 AC 在 `acceptance.md` 中有证据，抽查一两条测试确实在验证该 AC。
3. 迁移脚本：只新增、各方言一致、对存量数据安全、可在每个在用版本上执行。
4. 契约：破坏性修改已在设计中声明。
5. 自审报告中"需要 TL 重点看"的条目。
