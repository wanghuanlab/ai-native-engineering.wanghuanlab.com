# 合并前自审

建议在新会话中执行，避免沿用实现过程中的假设。

## 必读文件

1. `docs/changes/<REQ>/` 下的全部文件
2. 改动内容：`git diff main...HEAD`

## 检查项

1. **范围**：改动的文件是否都在 `tasks.md` 的「修改范围」内。
2. **完整性**：`spec-delta.md` 的每条 BR 是否都有实现，每条 AC 是否都在 `acceptance.md` 中有通过证据。
3. **数据库**：迁移脚本是否符合 `.ai/rules/30-database.md`；存量数据是否被正确处理；各方言是否一致。
4. **接口**：契约变更是否兼容；破坏性变更是否在 `design.md` 中声明。
5. **安全**：新增接口的权限、个人信息处理、日志中有无敏感信息、有无硬编码的密钥。
6. **质量**：N+1 查询、循环中访问数据库、异常被吞掉、事务边界错误。
7. **测试**：有无删除、跳过的测试，有无被改弱的断言。
8. **编码规范**：新增或修改的 Java 是否违反 `.ai/rules/25-alibaba-java.md` 的强制项，以及是否放宽了 `backend/quality/` 里的 Checkstyle、SpotBugs 或覆盖率下限。
9. **门禁**：运行 `./scripts/verify.sh full`。

## 输出

在 `acceptance.md` 末尾追加"自审报告"：

- 每个检查项的结论（通过 / 有问题）
- 问题清单：严重程度（高 / 中 / 低）、位置、说明、建议
- 需要 TL 重点看的地方（最多 5 条）

低严重度问题可以直接修复后重新自审；高严重度问题交给 TL 决定。

## 完成标准

- 没有未处理的高严重度问题，`verify.sh full` 通过。
- 工程师通知 TL 合并（流程见 `docs/context/collaboration.md`）。
