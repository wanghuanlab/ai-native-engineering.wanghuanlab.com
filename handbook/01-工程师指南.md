# 工程师指南

你对自己负责的需求从入库到验收全程负责。AI 起草和实现，你判断、求证、确认，并对结果负责。

## 第一次进入项目

```bash
git clone <仓库地址> && cd <项目>
./scripts/setup.sh
./scripts/verify.sh quick
```

然后读：`AGENTS.md`、`docs/context/collaboration.md`、`docs/context/architecture.md`、`docs/_templates/examples/` 中的示范变更包。

先确认项目密级（`AGENTS.md` 第一段）。涉密项目只能使用私有化部署的模型，**不要用云端 AI 工具打开仓库**。

## 一个需求怎么做

| 步骤 | 你说（对 AI） | AI 产出 | 你要做的 |
| :--- | :--- | :--- | :--- |
| 1 入库 | "执行 req-intake，需求材料在……" | `docs/requirements/<REQ>/intake.md` 和澄清问题 | 把口头需求写进 `raw/`（谁、何时、说了什么） |
| 2 澄清 | — | — | 逐条问 PM，把答复写进 `intake.md` |
| 3 规格 | "执行 spec-change" | `proposal.md`、`spec-delta.md` | 把"给 PM 的确认清单"发给 PM；**自己**登记确认记录 |
| 4 设计 | "执行 change-design" | `tasks.md`（L 级加 `design.md`） | 检查修改范围；L 级交 TL 审批 |
| 5 实现 | "执行 db-migration" → "执行 implement，从 T1 开始" | 迁移脚本、代码 | 每个任务完成后看一遍改动 |
| 6 验收 | "执行 test-accept" | 测试、`acceptance.md` | 做人工验证；**自己**填写验收结论 |
| 7 自审 | 新会话："执行 self-review" | 自审报告 | 处理问题；`verify.sh full` 通过后推送分支，通知 TL |
| 8 归档 | 发布后："把 spec-delta 合并进当前规格并归档" | 更新的 `docs/specs/` | 检查合并结果 |

S 级小改不需要变更包，但提交说明里必须有 `Refs:`。

## 必须记住的规则

- **确认区只能人填**：PM 确认记录、TL 审批、验收结论、部署回执，AI 不得填写。看到 AI 填了，删掉。
- **一个会话只做一个环节**，结束前让 AI 把进度写进 `tasks.md`。下次会话从 `tasks.md` 继续。
- AI 输出 `[需要人工决策]` 时，它在等你决定，不要让它"自己看着办"。
- 已合并的迁移脚本不能改；表结构变化一律新增脚本。
- 不要为了让校验通过而删除、跳过测试。确实因为业务变化要改测试，写进 `design.md` 由 TL 认可。
- 修改 `.ai/` 下的规则后，执行 `python3 scripts/build-ai-config.py`，生成的文件一起提交。

## 分支与提交

```bash
git switch -c feat/REQ-20261015-visitor-approval
git commit -m "feat(visitor): 新增访客预约审批流" -m "Refs: REQ-20261015-visitor-approval
AI-Assisted: cursor"
git fetch && git rebase origin/main
./scripts/verify.sh full
git push -u origin feat/REQ-20261015-visitor-approval
```

不能推送 main；推送后通知 TL，附上变更包路径。
