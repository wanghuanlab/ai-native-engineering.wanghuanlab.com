# 团队培训使用手册：用 AI 协作工程基线完成项目开发

> 适用对象：产品经理、工程师、技术负责人、运维实施和基线维护者。  
> 编写日期：2026-10-23。依据基线提交 `c4e1c3cbc552db5bf43cda273ca8628f41ae54a6`。  
> [打开图文培训版](training/index.html)：包含三张可交互的 Archify 图，可离线阅读和分发。本文为可维护的文字源。  
> 文中的园区任务是教学示例，不是待开发需求；示例 AC 和审批均不代表真实确认。

## 1. 先建立共同认识

本项目提供一套可以复制到业务项目的研发工作方式：把需求变成仓库内规格，让 AI 按明确范围实现，用测试和复核形成证据，最后交付到客户现场。团队共享的是流程、规则和工具；业务代码由各项目独立维护。

培训结束后，每位工程师应能完成四件事：判定任务级别；找到本阶段的输入与产物；给 AI 一条有范围、有验证方式的指令；说明需求、代码、测试和部署之间如何追溯。

请先区分两个工作目录：

| 你所在的仓库 | 在这里做什么 | 命令入口 |
| --- | --- | --- |
| 本仓库 `ai-native-engineering` | 维护基线、生成业务项目 | `bin/new-project.*`、`bin/selftest.sh` |
| 生成的业务项目，如 `park` | 写业务规格、代码、测试并发布 | `scripts/setup.*`、`scripts/new-change.*`、`scripts/verify.*` |

业务需求在生成的项目里开发。新建项目时复制一次骨架，后续通过版本同步升级规则和工具。它不提供现成的用户权限、组织机构等业务功能；这些能力仍需项目自己设计和验收。

## 2. 谁负责哪一个决定

| 角色 | 必须完成的工作 | 交接给下一位的依据 |
| --- | --- | --- |
| PM | 提供原始材料，回答澄清问题，确认业务规则与验收标准 | 工程师登记的真实确认记录 |
| 工程师 | 需求入库，驱动 AI，检查改动，测试和业务验收，维护检查点 | 变更包、逐条 AC 证据、自审报告 |
| TL | 认定分级，审批 L 级设计，复核合并，审阅发布并打标签 | 已审批设计、完整校验结果、版本交付包 |
| 运维 / 实施 | 按手册部署、升级并回填实际结果 | 部署回执、客户现场版本 |
| 基线维护组 | 维护模板、规则与门禁，发布基线版本 | 基线自测、变更说明、升级提示 |
| AI | 起草规格、设计、实现、测试和报告 | 可由人审阅的文件和真实执行证据 |

AI 不填写 PM 确认、TL 审批、人工验收结论和部署回执。PM 不必操作 Git：工程师把确认清单交给 PM，得到回复后本人登记确认人、时间、方式和原话或截图。AI 的“理解了”不能替代这一步。

## 3. 第一天：创建或加入项目

### 3.1 TL 创建业务项目

准备 Git、Python 3.10+、uv 或 Copier、JDK 21、Docker、Node.js 22+、pnpm 11。具体依赖版本以生成项目的锁定配置为准。

在**基线仓库根目录**运行：

```bash
bin/new-project.sh ~/work/park
```

交互填写项目代号、名称、包名前缀、TL 的 Git 用户名、密级、信创画像、数据库、大屏选项和示例模块选项。普通 / 受限 / 涉密决定能用哪些 AI 服务；先确认密级，再用 AI 打开项目。涉密项目仅用内网私有化模型。

基线来源必须是团队可访问的 Git 地址，固定到标签或提交。默认采用本仓库的 origin；需要指定时使用 `--source <Git地址>` 与 `--ref <已发布引用>`。不要把创建者电脑上的目录作为团队升级来源。

进入**生成的业务项目**：

```bash
cd ~/work/park
./scripts/setup.sh
./scripts/verify.sh quick
```

Windows cmd 对应操作：

```bat
bin\new-project.cmd %USERPROFILE%\work\park
cd %USERPROFILE%\work\park
scripts\setup.cmd
scripts\verify.cmd quick
```

Windows 也有同名 `.ps1` 入口；不需要为了日常命令安装 WSL。`new-project` 在基线仓库运行，其余命令在生成项目中运行。

TL 按团队规范完成初始提交和业务仓库配置。需要服务端限制时，由服务器管理员安装 `tools/server-hooks/pre-receive` 并配置 TL 身份；本地 setup 不会自动替你部署服务端钩子。

### 3.2 工程师加入已有项目

克隆业务项目，执行 setup 和 quick。先读 `AGENTS.md`、`docs/context/collaboration.md`、`docs/context/architecture.md`、`docs/context/pitfalls.md`，再看相关能力规格和 `docs/_templates/examples/` 的完整示例。

需要本地联调时，先启动 Docker，再分别打开终端运行：

```bash
# 业务项目根目录：启动本地数据库
docker compose -f deploy/local/compose.yaml up -d

# 后端终端
cd backend
./mvnw install
./mvnw -pl app spring-boot:run

# 前端终端，从项目根目录进入
cd frontend
pnpm gen:api
pnpm dev
```

模板默认后端为 `http://localhost:8080`、接口文档为 `/doc.html`、前端为 `http://localhost:5173`。以项目实际配置和启动日志为准。首次 `install` 会执行测试，需要 Docker 可用；不要用跳过测试作为排错方式。

## 4. 接到任务，先分级

分级由工程师提出、TL 认定；满足任一更高等级条件就升级，拿不准取高。

| 等级 | 判定条件 | 必要产物 | 进入实现的条件 |
| --- | --- | --- | --- |
| S 小改 | 单模块内，不改表、不改接口、不改业务规则 | 规范提交说明，含 `Refs:` | 明确范围，按影响验证，TL 合并复核 |
| M 常规 | 单模块新增功能或调整业务规则；表结构只新增表或字段，且没有 L 级因素 | `proposal.md`、`spec-delta.md`、`tasks.md`、`acceptance.md` | PM 已确认，任务范围与验证命令齐全 |
| L 重大 | 改删已有字段、处理存量数据、修改已发布接口、跨模块，或涉及权限、安全、个人信息 | M 级产物加 `design.md` | PM 已确认，TL 已审批技术设计 |

文字修正可属于 S；新增单模块查询能力且不触及已有接口和权限规则可属于 M；更改预约审批权限或在用接口属于 L。缺陷也按影响分级，并先写可复现缺陷的测试。

**S 级免变更包，不免验证、Refs 和复核。** M / L 级不能从一句“帮我做个页面”直接进入编码。

## 5. 按标准流程推进一个需求

<!-- diagram:delivery-flow -->

图 2 是 M / L 级标准路径。每一阶段先满足放行条件，再把产物交给下一阶段。需求发生变化时，新建变更包；不要靠会话中一句口头补充悄悄改掉已确认规格。

| 阶段 | 使用的 Skill | 主要输入 → 输出 | 这一阶段怎样才算完成 |
| --- | --- | --- | --- |
| 入库与澄清 | `req-intake` | 原始材料、当前规格 → `raw/`、`intake.md` | 问题有答案或明确本期不做；有分级建议 |
| 规格 | `spec-change` | 澄清结论 → 提案、规格增量、PM 确认清单 | BR 被 AC 覆盖；PM 真实确认，工程师登记 |
| 设计与计划 | `change-design` | 已确认规格、代码与上下文 → `tasks.md`，L 加设计 | 范围和验证命令齐全，L 已获 TL 审批 |
| 数据库 | `db-migration` | 设计、历史迁移、方言配置 → 新迁移、实体、结构摘要 | 各启用方言齐全，完成相应数据库验证 |
| 实现 | `implement` | 任务、规格、设计 → 契约、后端、前端 | 逐项验证并更新任务，quick 通过 |
| 测试与验收 | `test-accept` | 每条 AC → 测试和 `acceptance.md` | 每条 AC 有证据，工程师完成人工验收，full 通过 |
| 自审与合并 | `self-review` | 变更包与差异 → 自审报告 | 处理问题，TL 复核并合并 |
| 发布 | `release-pack` | 提交、迁移、配置、客户版本 → 发布与升级手册、交付包 | TL 审阅，真实升级验证，打标签后打包 |
| 部署与归档 | 运维部署；工程师归档 | 交付包 → 回执、更新台账与当前规格 | 现场版本可查，`docs/specs/` 与已发布行为一致 |

### 5.1 先创建需求容器

以下命令在业务项目根目录执行：

```bash
./scripts/new-change.sh visitor-approval --intake-only
# 澄清完成、分级经 TL 认定后，再创建变更包
./scripts/new-change.sh visitor-approval --level L
```

脚本会输出实际 REQ 编号。相同短名沿用已有编号，已归档短名不能用于新变更。教学中以下统一用 `<REQ>` 表示实际输出，例如 `REQ-20261023-visitor-approval`；尖括号占位符需替换后再执行命令。

原始材料放到 `docs/requirements/<REQ>/raw/`。口头需求也要记录“谁、何时、通过什么方式、原话是什么”。

### 5.2 用 BR 与 AC 写清楚业务

以“预约增加审批”为例，这是涉及权限和已有接口的 **L 级教学示例**。先澄清：谁审批，驳回后能否重提，旧预约是否免审，待审批能否核销，并发审批如何处理。答案来自 PM，不能让 AI 自行补齐后直接编码。

下面是**假设 PM 选择了旧预约免审**后的示例写法，编号须按实际能力已有编号递增：

```text
BR-visitor-01：新建预约需要审批通过后才可核销。
BR-visitor-02：升级前已有预约保持原有核销行为。

AC-visitor-01
前提：一条新建预约处于待审批状态。
操作：核销人员尝试核销。
结果：核销被拒绝，预约状态保持不变。

AC-visitor-02
前提：存在升级前创建且原本允许核销的预约。
操作：升级后执行核销。
结果：核销成功，不要求补做审批。
```

“页面正常”“接口没问题”不足以验收。规则要覆盖正常、异常、权限、状态和存量兼容；每条 AC 都应能找到测试或人工操作记录。

### 5.3 把设计拆成能完成的任务

`tasks.md` 兼作修改授权范围和会话检查点。新模块如果要通过脚手架创建，还要把它会修改的父 POM、app 依赖、契约与架构文档列入范围。

```markdown
## 修改范围
- 允许：backend/modules/visitor/**
- 允许：backend/app/src/test/**
- 允许：contracts/openapi/visitor.yaml
- 允许：db/migration/**/V20261023*__visitor_*.sql
- 允许：frontend/apps/admin/src/views/visitor/**
- 允许：docs/context/db-schema.md、docs/changes/<REQ>/**
- 禁止：其他业务模块、基线托管文件、生成代码

## 任务
- [ ] T1 新迁移与旧数据兼容。验证：./scripts/verify.sh db
- [ ] T2 更新契约并生成客户端。验证：./scripts/verify.sh frontend
- [ ] T3 实现领域规则与接口。验证：./scripts/verify.sh backend
- [ ] T4 页面与交互。验证：./scripts/verify.sh frontend
- [ ] T5 AC 测试与验收报告。验证：./scripts/verify.sh full
```

这是结构示例，不能原样作为真实修改授权。每项完成后记录实际验证结果；`db` 只检查迁移文件规则，不等于 SQL 已在真实数据库执行成功。

### 5.4 按工程约定实现

先迁移与契约，再后端和前端。后端按 `domain → service → web` 实现；事务边界放在 service，Controller 不直接注入 Repository，模块间只通过 `api` 包协作。

前后端共享 `contracts/openapi/` 契约。改契约后执行生成，Controller 实现生成的接口，前端使用生成的客户端。不得直接修补生成结果来掩盖契约错误。

迁移新增为 `V<年月日时分>__<模块>_<描述>.sql`；每个启用方言目录提供同名文件。合并前检查版本号冲突，同一分钟并行创建脚本仍可能撞号。已合并脚本只读；结构摘要用 `./scripts/db-schema.sh` 从真实测试数据库生成。

### 5.5 验收需要证据

| AC | 合适的验证 | 应保留的证据 |
| --- | --- | --- |
| 待审批不能核销 | 领域 / 接口测试 | 测试类与方法，实际执行结果 |
| 未授权人员不能审批 | 权限集成测试 | 身份、请求、响应和状态断言 |
| 旧预约兼容 | 先构造旧数据，再迁移并验证 | 数据准备、升级过程、断言结果 |
| 页面提示与操作反馈 | 适合时做页面测试，或人工验证 | 操作步骤、截图、实际结果，由工程师确认 |

AI 可以整理自动化证据并起草报告。人工操作尚未执行就写“待验证”；不能把建议测试当成已通过测试。

## 6. 怎样给 AI 下指令、怎样换会话

项目内八个标准 Skill 是流程入口。不同工具调用方式不同，可以直接用自然语言说“执行 req-intake”；如果工具没有自动发现 Skill，让它读取项目对应的 `.ai/skills/<名称>/SKILL.md` 后执行。

### 6.1 四种可直接改写的提示词

**需求入库：**

```text
执行 req-intake。需求材料在 docs/requirements/<REQ>/raw/。
先读术语、相关当前规格和进行中的变更包，整理 intake.md，提出澄清问题和分级理由。
本会话只做入库与澄清，不写业务代码。不要把建议答案当成 PM 已确认答案。
```

**设计：**

```text
执行 change-design，变更包为 docs/changes/<REQ>/。
核实 PM 确认记录，分析表、接口、模块、页面、已有测试和存量数据影响。
产出有明确修改范围、任务顺序和验证命令的 tasks.md；L 级补 design.md。
列出风险和需要 TL 决定的内容，审批区留给人填写。
```

**继续实现：**

```text
读取 docs/changes/<REQ>/tasks.md、spec-delta.md、已批准的 design.md、
相关当前规格和 pitfalls.md；执行 implement，仅完成第一个未完成任务。
先核对修改范围。运行对应验证，通过后勾选任务，记录结果、遗留问题和下一步。
需要越界、引入依赖或发现规格冲突时，输出 [需要人工决策] 并说明原因与选项。
```

**自审：**

```text
在新会话执行 self-review，变更包为 docs/changes/<REQ>/。
对照当前主干差异检查范围、BR 实现、AC 证据、迁移、契约、安全和测试变化。
运行 full，把真实结果与需 TL 重点关注的问题写入 acceptance.md 的自审报告。
不代填人工验收结论，不推送 main。
```

### 6.2 一个会话做一个环节

规范要求一个会话只做一个环节，实现阶段按适合单会话的任务继续。结束前在 `tasks.md` 记录：完成了什么、执行了什么验证、哪里失败、有哪些注意事项、下一个未完成任务。尚未产生 `tasks.md` 的入库和规格阶段，在本阶段文档记录进展。

换人、隔天、换工具都从仓库文件恢复。不要依赖“你还记得上次吗”。同一分支不要让多个 AI 会话同时改代码；需要并行时先稳定契约和迁移，再使用独立工作树与互不重叠的范围。

### 6.3 哪些情况必须暂停给人决策

M / L 级缺变更包；L 级未审批；需要越出修改范围；改删已有字段或表、清空数据；破坏已发布接口；新增第三方依赖；旧测试因业务变化而失败；同一问题连续修复三次失败；需求与当前规格冲突。

AI 输出 `[需要人工决策]`，说明触发原因、影响和选项。工程师或 TL 作出明确决定，必要时更新规格、设计、范围和审批，再继续；不要用“自己看着办”代替决策。

## 7. 质量门禁：执行什么、证明什么

<!-- diagram:quality-gates -->

| 命令 / 时机 | 当前脚本执行的检查 | 使用建议 |
| --- | --- | --- |
| commit | 暂存的托管文件、迁移、密钥、AI 配置一致性；commit-msg 检查说明 | 提交前避免把错误文件纳入版本 |
| `verify ai` | AI 配置与规则源一致性 | 修改项目规则并重新生成后执行 |
| `verify db` | 迁移命名、方言文件对应、已合并脚本不可变 | 不代表所有方言 SQL 语义等价 |
| `verify backend` | Spotless、Checkstyle、单元测试、SpotBugs | 后端任务局部验证 |
| `verify frontend` | API 生成、类型、Lint、格式、测试 | 前端任务局部验证 |
| `verify quick` | AI、迁移、后端上述检查、前端上述检查 | 推送钩子调用，日常实现完成时运行 |
| `verify full` | AI、迁移、测试变化检查、全仓密钥扫描、Maven verify 和覆盖率、前端检查与构建、升级路径 | 合并、验收、发布前的完整入口 |
| `verify upgrade` | 台账在用版本到当前 PostgreSQL 迁移 SQL 路径 | 发布前结合台账验证 |

表中的 `verify` 指 `./scripts/verify.sh`，Windows 用 `scripts\verify.cmd`。默认模式是 quick。任一步失败会返回非零，修复该失败再继续。

需要格式化时用工具，而不是降低规则：

```bash
# 业务项目根目录
(cd backend && ./mvnw spotless:apply)
(cd frontend && pnpm format)
./scripts/verify.sh quick
```

### 7.1 培训时必须说明的当前能力边界

1. **full 不能判断业务是否正确。** AC 是否充分、权限设计是否合理、断言是否真实覆盖规则，仍由工程师和 TL 审查。脚本检查测试变化不能替代语义审查。
2. **当前有覆盖率下限。** `verify.py` 读取 `backend/quality/coverage-minimum.txt`，报告缺失、无统计行或低于下限都会失败。方案正文中“覆盖率只告警”的表述不能当作当前执行行为。
3. **升级路径脚本只验证 PostgreSQL 的 SQL 路径。** 它不证明所有存量业务数据、应用功能和信创方言都正确；信创需安排目标库验证。台账没有在用版本时该步骤明确跳过，不能汇报成“全部客户版本升级已通过”。
4. **契约生成不等于自动兼容检测。** 当前 verify 入口没有独立的 OpenAPI 破坏性差异检查步骤，TL 仍需审阅在用接口的兼容性及 L 级设计。
5. **本地钩子可以绕过。** TL 合并复核是团队必经流程；机器强制程度取决于服务端钩子和身份配置。不要把本地 Git 用户名校验当作可靠身份认证。

规则与手册冲突时，以业务项目实际 `.ai/rules/` 为准并提交改进提案；描述工具行为时同时核对实际脚本。

## 8. 提交、合并与发布交接

### 8.1 工程师交给 TL

业务项目的约定分支为 `feat/<REQ>` 或 `fix/<BUG>`。提交说明使用中文描述，S 级也要有 Refs；使用 AI 时保留 AI-Assisted：

```text
feat(visitor): 增加预约审批与核销校验

Refs: REQ-20261023-visitor-approval
AI-Assisted: codex
```

提交前检查暂存范围。准备交接时更新到最新主干并处理冲突，在准备交付的状态运行 full，再推送功能分支。交接信息包含：分支、REQ、变更包路径、AC 结果、完整校验结果、未决风险。由工程师通知 TL。

TL 阅读变更包、PM 确认与 L 级审批，抽查 AC 和实现，重点检查迁移、契约、权限、安全与存量兼容；在待合并状态执行 full，意见处理后合并并推送 main。**建议在实际合并结果上再核验必要检查**，避免多个功能单独通过但组合后失败；这是额外的培训建议，不应描述为现有脚本已强制执行。

### 8.2 TL 发布，运维部署

TL 发起 release-pack，AI 起草三份文件：

```text
docs/releases/<版本>/release-notes.md
docs/releases/<版本>/deploy-guide.md
docs/releases/<版本>/upgrade-guide.md
```

升级手册覆盖 `docs/releases/deployments.md` 的全部在用版本，并列明数据库、配置、停机与回退方式。不确定耗时写“待确认”，不得编造执行结论。TL 审阅、提交发布文档并打标签后运行：

```bash
./scripts/release-pack.sh <版本>
# 需要 amd64 / arm64 离线镜像包时，按发布计划使用 --images
```

交付包中应有应用、各方言迁移、配置模板、发布说明、部署和升级手册、校验和；镜像按需提供。运维先核对校验和，备份数据库，再执行独立迁移，最后启动生产应用并验收。具体命令采用本版本交付包手册，不能让应用启动自动代替生产迁移。

部署回执记录客户现场、升级前后版本、时间、成功或失败、异常情况。更新台账的“在用版本”清单，这会影响下一次升级测试的起点。

### 8.3 发布后完成规格归档

工程师把本次 `spec-delta.md` 合并到对应 `docs/specs/<能力>/spec.md`，将变更包移动到 `docs/changes/archive/`，补充踩坑与决策记录。多个需求同时修改同一规格时，以最新已发布规格合并增量，人工检查不能丢掉其他需求。

此后看当前规格就能知道系统现状，看归档包能知道为什么变更。

## 9. 基线升级与经验回流

升级前保持工作区干净，核对新版本变化与兼容提示，在业务项目运行：

```bash
./scripts/sync-baseline.sh <基线版本>
./scripts/verify.sh full
```

来源不可达或仍是旧的本机路径时，用 `--source <团队Git地址>` 修正。同步可能产生共同维护文件的冲突，逐项处理、验证后提交。业务项目版本和基线版本是两套编号，不要混淆。

项目要加自己的规则，写 `.ai/project/` 后执行 `python3 scripts/build-ai-config.py`，将生成结果一起提交。共性缺陷与改进提交到基线仓库 `proposals/`，不要在项目里修改托管门禁来“临时放行”。

基线维护者修改模板、规则或脚本后，使用 `bin/selftest.sh all` 验证三种画像和门禁拦截；单独检查来源与 Copier 更新使用 `bin/selftest.sh source`。

## 10. 团队培训怎么讲、怎么练

下面是建议的 **90 分钟培训安排**，时间是教学安排，不是项目开发工时估算。

| 时间 | 讲师活动 | 学员当场完成 |
| --- | --- | --- |
| 0～10 分钟 | 用图 1 解释基线、骨架、项目、文件归属 | 判断脚本、业务代码、POM 分别在哪改 |
| 10～25 分钟 | 演示创建 / 加入项目，读取规则并运行 quick | 找到本项目密级、TL、基线版本 |
| 25～45 分钟 | 用图 2 走访客审批示例，演示入库与规格 | 提出至少三条澄清问题，写两条可测试 AC |
| 45～60 分钟 | 演示设计与任务检查点、恢复会话 | 为一项任务写范围、验证命令和交接备注 |
| 60～75 分钟 | 用图 3 演示门禁结果与 AC 证据 | 区分“db 文件检查通过”和“真实迁移通过” |
| 75～90 分钟 | 演示 TL 交接、发布、回执、归档 | 说明需求到部署的完整追溯链 |

### 10.1 在演练项目中做三道题

1. **S 级练习：** 修正一个静态文案错字，不改变业务含义。说明为何是 S，给出带 Refs 的提交说明和验证方式。
2. **L 级练习：** 为访客审批写 intake、规格增量、设计与任务草稿。审批区保持空白，由扮演 PM / TL 的人实际确认后再进入实现。
3. **恢复练习：** 在一项任务完成后关闭会话，换一位同事只读取仓库文件继续。无法继续的地方补进检查点。

教学环境使用虚构数据和独立项目。权限、存量数据、客户升级验证需保留在任务中，不能因为课堂时间不足从验收范围里删掉；课堂可以明确停在某一阶段。

### 10.2 学员完成标准

- [ ] 能分清基线仓库与业务项目的命令入口。
- [ ] 能按条件判断 S / M / L，说明谁认定、谁确认。
- [ ] 知道 raw、intake、当前规格、规格增量、设计、任务和验收报告各自用途。
- [ ] 能把需求写成“前提 / 操作 / 结果”，为 AC 指定证据。
- [ ] 给 AI 的任务包含本阶段、输入、范围、验证和暂停条件。
- [ ] 能使用任务检查点换人、换工具恢复工作。
- [ ] 能解释 quick / full 与人工复核的边界，遇到失败不绕过。
- [ ] 能把 REQ、提交、测试、发布版本和客户部署回执串起来。

## 11. 常见问题速查

| 现象 | 正确处理 |
| --- | --- |
| AI 上来就写代码 | 先检查分级，M / L 补齐需求、确认与计划 |
| 修改被托管文件检查拦截 | 看归属，项目规则进 `.ai/project/`；共性改动回基线 |
| 生成配置不同步 | 修规则源，重跑 build-ai-config，不直接改生成文件 |
| 需要增加依赖或改别的模块 | 暂停说明影响，更新设计 / 范围并取得对应决策 |
| 旧测试失败，AI 想改断言 | 判断是否真实业务变化，先记录设计与 TL 意见 |
| 前端和后端字段对不上 | 修 OpenAPI 契约并重新生成两端 |
| 旧迁移写错了 | 已合并的脚本保持只读，设计新增修复迁移 |
| 同一错误连续修三次失败 | 保留失败证据，交人决策，避免继续猜测 |
| full 通过，台账却没有客户版本 | 升级步骤可能跳过；补真实台账与版本标签后验证 |
| 新会话不知道做什么 | 补 tasks 的状态、结果、注意事项和下一步 |
